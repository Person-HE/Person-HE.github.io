从"为什么需要安全"到"如何实现安全"的完整思考链路

第一阶段：需求分析与技术选型

身份认证

问题描述-怎么实现

项目最开始，我需要实现用户登录注册功能。我第一个想到的是：用户登录后，服务端把用户信息存到Session里，返回一个SessionID给浏览器，浏览器每次请求带上这个ID。

但是仔细思考后发现Session方案有几个问题：

  1. 服务端有状态：每个用户登录都要在服务端存Session数据。如果用户量大，服务端内存压力大
  2. 不支持分布式：项目如果部署多个服务实例，用户A登录在实例1，下次请求路由到实例2，实例2没有Session数据，用户就需要重新登录
  3. 跨域问题：现代前端和后端通常分离部署在不同域名，Session的Cookie跨域携带很麻烦
  4. 移动端不友好：移动端App没有Cookie机制，Session方案不适用

确定了JWT+Redis方案后，又遇到新问题：Token有效期设多久？

如果有效期很短（比如30分钟），用户体验差：用户正看着页面，突然就过期了，需要重新登录。

如果有效期很长（比如7天），安全性差：Token泄露后，攻击者有7天的使用时间。

技术选型：Session vs JWT vs OAuth2.0

认证方案技术选型对比

方案 原理 优点 缺点 适合场景
A: Session 服务端存储会话 客户端存Cookie 服务端可控 可随时失效 服务器有状态 不支持分布式 CSRF风险 传统单体应用
B: JWT单Token 客户端存Token 服务端无状态验证 无状态易扩展 跨域友好 Token无法主动失效 泄露后危险期长 简单API服务
**C: JWT双Token ****** Access(短期)+Refresh(长期) Redis黑名单管理 安全性高 无感刷新 可控失效 实现稍复杂 我们选这个
D: OAuth2.0 授权码模式 第三方授权登录 标准化 支持第三方 复杂度高 需授权服务器 大型开放平台

我的选择过程：

  1. 排除Session：项目是微服务架构（Gateway + 多个Service），Session无法在多实例间共享。虽然可以用Redis存Session，但那本质上就是自己造轮子了。最关键点在于如果项目支持小程序，浏览器，APP，session没有办法多端共享
  2. 考虑过OAuth2.0：但项目目前没有第三方登录需求，引入OAuth2.0太重了（Spring Security OAuth2已经废弃，要用Spring Authorization Server）。
  3. 最终选JWT双Token：
  • Access Token（2小时）：短期有效，即使泄露损失有限
  • Refresh Token（7天）：长期有效但只能用于换新Token，不能访问业务接口
  • Redis黑名单：用户登出时将Token加入黑名单，解决"无法主动失效"问题

所以综合考虑之下，最合理，合适的方案就是JWT双Token，不仅支持多端，双Token一定程度下保证了安全性，而且实现起来比起OAuth2.0要简单

JWT数据结构设计

JWT主要是三个字段：Header，Claims，Signautre

Header： 指定**加密算法**、令牌类型，告诉后端：这是 JWT，用什么算法验签。

Claims： 存**业务数据：用户ID、角色、过期时间、签发人等，一定不能放敏感数据**。 存放用户身份信息，后端拿到后就能直接查看到用户的身份信息，不需要查询数据库了

Signature：用头部算法 + 秘钥对前两段加密生成，**作用防篡改**：只要Header或Claims被改，签名立马失效，后端一眼就能识别伪造

Claim字段 说明 Access Token Refresh Token
userId 用户唯一标识 有 有
username 用户名（便于日志追踪） 有 有
type Token类型标识 "access" "refresh"
iat 签发时间（Issued At） 有 有
exp 过期时间（Expiration） +2小时 +7天

权限控制

第一次问题描述-怎么实现

项目中有多种资源：帖子、评论、圈子、用户资料等。每种资源都有不同的操作权限：

  1. 帖子：作者可以编辑/删除自己的帖子，圈主/管理员可以删除任何帖子
  2. 评论：作者可以删除自己的评论，圈主可以删除任何评论
  3. 圈子：只有圈主可以删除圈子，管理员可以管理成员
  4. 用户资料：用户只能修改自己的资料

最开始，我在每个Controller方法里都写了权限判断代码，但是发现存在一些问题：

  1. 代码重复：每个需要权限判断的方法都写一遍类似的逻辑
  2. 权限逻辑与业务逻辑耦合：方法里一半代码在做权限判断，一半在做业务
  3. 容易遗漏：忘记加权限判断，就会造成越权漏洞
  4. 难以维护：权限规则变了，要改很多地方

就这样写下去，越来越多的业务和判断真的把脑子都搞炸了，一团糊的情况

第一次技术选择

在方法上加@RequirePermission(resource = POST, action = DELETE)，AOP切面自动拦截并校验权限。业务方法里完全没有权限判断代码，只关心业务逻辑。权限规则变了，只需改切面或Checker（具体的业务模块下的权限控制类）实现，Controller不用动

第二次出现问题-优化

确定了注解+AOP方案后，又遇到新问题：不同资源的权限判断逻辑完全不同。

帖子权限：判断是否是作者，或是否是圈子的管理员/圈主

圈子权限：判断是否是圈主，或是否是管理员

评论权限：判断是否是作者，或是否是帖子的圈主/管理员

用户资料权限：判断是否是用户本人

如果所有判断逻辑都写在AOP切面里，切面类会变成一个巨大的switch-case，违反了开闭原则：对扩展开放，对修改封闭。新增资源类型时，不应该修改已有的切面代码

第二次优化解决-策略模式

  1. 定义一个PermissionChecker接口，包含check()方法
  2. 每种资源一个实现类：PostPermissionChecker、CirclePermissionChecker等
  3. AOP切面不写具体判断逻辑，而是根据资源类型，路由到对应的Checker

为什么要这样设计？

如果不用策略模式，所有判断逻辑堆在切面里：

切面类会超过500行，难以阅读和维护

新增资源类型要修改切面类，违反开闭原则

不同资源的判断逻辑互相影响，改帖子权限可能不小心改坏圈子权限

用策略模式后：

切面类只有20行，只做路由分发

新增资源类型只需添加新Checker实现类，不需要改切面

每种资源的判断逻辑独立，互不影响

第二阶段：数据安全与加密策略

密码加密

问题描述

对于这些敏感数据，采用明文存储是非常严重的问题，所以要采用加密存储

方案对比与选择

方案 加密方式 数据库泄露后 破解难度 我的评估
明文 不加密 直接看到所有密码 0秒 不可接受
MD5 hash("123456") 彩虹表秒破 <1秒 不可接受
加盐MD5 hash("123456" + salt) 需要逐个暴力破解 分钟级 勉强可用但不够
BCrypt bcrypt("123456", salt, cost=12) 逐个破解，每个400ms 数年 我们选这个

我的选择理由：

  1. BCrypt自动加盐：每次加密都用随机盐值，同一个密码"123456"，每次加密出来的结果都不一样。黑客就算有彩虹表也完全没用。
  2. 计算成本可控：通过cost参数调节计算复杂度。cost=12意味着2^12=4096轮迭代，单次验证约100-200ms。看起来慢，但登录接口本来就不需要高频调用，这个性能损耗完全可接受。
  3. Spring Security内置支持：不需要自己实现，直接用BCryptPasswordEncoder，成熟可靠。
  4. 如果密码只是简单MD5，数据库泄露后，黑客用GPU+彩虹表，1秒破解数亿条密码。用户在其他网站用相同密码的，也会被批量撞库。

敏感数据存储

问题描述

手机号，邮箱这些敏感数据在数据库中怎么存？要避免内部人员查看和泄露数据

方案对比

方案 思路 优点 缺点 我的评估
明文存储 直接存 查询方便 谁都能看 不可接受
哈希存储 hash(手机号) 无法反推 无法解密，业务用不了 不可用
AES加密 加密后存储，需要时解密 可逆加密，业务可用 密钥管理是挑战 我们选这个
脱敏存储 只存脱敏后的数据 安全 原始数据丢失，无法发短信 不可用

我的选择理由：

  1. 业务需要可逆：我需要给用户发短信验证码、找回密码，所以必须能还原手机号。哈希方案直接pass。
  2. AES对称加密够用：手机号不需要非对称加密（那是用来传输的），对称加密性能更好，256位密钥已经足够安全。
  3. 如果手机号明文存储，DBA可以一键导出所有手机号。或者数据库备份泄露，黑客可以直接给用户发诈骗短信。

隐私安全：信息返回前端

问题描述

通过API返回给前端的数据，需要进行脱敏处理，保证用户信息的隐私

比如：点外卖的单子上的手机号通过只展示前后几位数字，中间的都用*代替，保护了用户的信息

用户A登录后，接口返回了完整的邮箱和手机号。

如果用户在咖啡厅使用公共WiFi，响应数据可能被中间人截取。

或者用户浏览器的开发者工具被其他人看到。

方案对比

方案 思路 优点 缺点 我的评估
全部返回 前端拿到完整数据 实现简单 隐私泄露风险 不可接受
只返回脱敏数据 接口只返回z_n@e_.com 安全 用户不知道自己邮箱对不对 体验差
敏感数据脱敏 返回部分隐藏的数据 安全+体验平衡 需要额外处理 我们选这个

我的选择理由：

  1. 脱敏规则要统一：邮箱保留首尾字符、手机号保留前3后4、用户名保留首字符。这样用户能确认是自己的数据，又不会泄露完整信息。
  2. 脱敏在后端完成：不在前端做脱敏，因为前端代码可被修改，不可信。后端脱敏后，传输到前端的就是安全的数据。
  3. 日志也要脱敏：操作日志中如果记录了邮箱和手机号，日志泄露同样会造成隐私问题。

JWT无状态-Token失效问题

问题描述

用户登出或者改密码后，旧Token还是有效的，怎么办？

JWT是无状态的，验证时只需要用secret验签即可，不查数据库。

这意味着：一旦Token签发，在过期之前（我的Access Token是2小时），它始终有效。

如果用户点击"退出登录"，或者修改了密码，旧Token仍然可以访问接口！

所以通过Redis黑名单机制解决Token失效问题

方案对比

方案 思路 优点 缺点 我的评估
方案A：缩短Token有效期 Access Token设为5分钟 泄露窗口小 用户频繁需要刷新Token，体验极差 不可接受
方案B：每次都查数据库 验证Token时查DB确认是否有效 可实时失效 每次请求都查DB，性能灾难 不可接受
方案C：Redis黑名单 登出时将Token加入Redis黑名单，带TTL 可主动失效，性能好 需要额外Redis存储 我们选这个

我的选择理由：

  1. Redis性能好：黑名单检查是Redis GET操作，耗时<1ms，不影响整体性能。
  2. TTL自动清理：设置过期时间与Token剩余有效期一致，过期后Redis自动删除，不用手动清理。
  3. Key设计简单：blacklist:{token值}，验证Token时先检查是否在黑名单中。
  4. 用户修改密码后，旧Token仍然有效。如果旧Token被别人获取（比如在公共电脑登录过），别人可以继续以该用户身份操作。

Token刷新机制

问题描述

Access Token过期了，怎么让用户无感续期？

如果Access Token只有2小时有效期，用户正在操作时突然Token过期，被迫重新登录，体验极差。

但如果把Token有效期设为7天，一旦泄露，损失更大。

双Token的设计思路

Access Token（短期，2小时）：，用于访问业务接口，每次请求携带在Header中，过期后自动调用刷新接口

Refresh Token（长期，7天）：仅用于换取新的Access Token，不能用来访问业务接口，刷新接口会验证它是否是真正的Refresh Token

即使Access Token泄露，攻击者只有2小时的使用窗口。

即使Refresh Token泄露，攻击者只能刷新Token，不能访问业务接口。

为什么要区分Token类型？ 如果只有一个Token，过期时间长则风险大，过期时间短则体验差。双Token把"访问权限"和"续期权限"分开，各自有不同的安全等级。

为什么Refresh Token不能访问业务接口？ 在JWT的Claims中加一个type字段，验证时检查type是否为"access"。这样即使攻击者拿到Refresh Token，也无法调用/api/v1/post/list等接口。

刷新时是否要换新的Refresh Token？ 我的项目实现是每次刷新都发放新的双Token。这样可以限制Refresh Token的使用次数，如果被他人获取也能及时失效。

限流

问题描述

如何防止单个IP或单个用户高频调用？

攻击者针对登录接口发起大量请求，每秒几百次；即使有登录失败限制，每次请求仍然会消耗服务器资源（查DB、BCrypt计算）；如果攻击者同时攻击多个接口，服务器可能被打垮

限流方案对比

方案 思路 优点 缺点 我的评估
不限制 来多少处理多少 实现简单 服务器被打垮 不可接受
Gateway全局限流 每个IP+路径，每秒最多100次 所有请求统一拦截 无法针对具体接口精细化控制 第一层防御
Service方法级限流 针对具体接口（如登录），每IP每分钟最多10次 精细控制 需要在每个方法上加注解 第二层防御
两层结合 Gateway全局限流 + Service方法级限流 纵深防御，越限越少 实现稍复杂 我们选这个

我的选择理由：

  1. Gateway全局限流是第一道防线：所有请求都经过Gateway，在此做一层粗粒度的限流（如每个IP每秒100次）。这能挡住大部分暴力攻击，防止服务器被直接打垮。
  2. Service方法级限流是第二道防线：对于特别敏感的接口（如登录、发送验证码），加上@RateLimit注解，设置更严格的限制（如每IP每分钟10次）。这样即使Gateway层放行了，Service层还有更精细的控制。
  3. 限流维度支持IP和用户：未登录的请求按IP限流，已登录的请求按userId限流，防止单个用户滥用接口。
  4. Redis滑动窗口实现：不是简单的固定窗口（如每分钟重置），而是滑动窗口，更精确地控制频率。
  5. 如果没有限流，攻击者针对登录接口发起大量请求，即使每个请求都被拒绝（密码错误），每次BCrypt计算耗时100ms，1000个并发请求就能让服务器卡死。这是典型的资源耗尽攻击。

防暴力破解：登录失败限制

问题描述

攻击者每秒尝试数千次密码怎么办？

攻击者准备了一个常见密码字典（123456、password等10000个密码），用脚本针对某个邮箱批量尝试这些密码，如果没有限制，每秒可以尝试数千次，10000个密码，只要这个用户用了常见密码，几分钟内就会被破解

方案对比

方案 思路 优点 缺点 我的评估
不限制 允许无限次尝试 不会误伤正常用户 暴力破解毫无阻碍 不可接受
固定延迟 每次密码验证后sleep 1秒 减缓攻击速度 正常用户也受影响 体验差
失败计数+锁定 失败5次要求验证码，10次锁定15分钟 有效阻止自动化攻击 可能误伤忘记密码的用户 我们选这个
渐进式延迟 失败次数越多，等待时间越长 温和限制 实现稍复杂 可作为补充

我的选择理由：

  1. 渐进式限制：不是上来就锁定账户，而是5次要验证码，10次才锁定。这样正常用户输错几次密码不会立刻被锁。
  2. Redis存储而非MySQL：读写速度快，自动过期，不影响主库性能。失败计数是高频操作，放Redis最合适。
  3. 锁定时间15分钟：足够阻止自动化攻击（攻击脚本不会等15分钟），又不会让用户等太久。
  4. **不区分"用户不存在"和"密码错误"**：防止攻击者通过响应差异枚举有效邮箱。统一返回"邮箱或密码错误"
  5. 如果没有限制，攻击者拿到邮箱列表后，用脚本批量尝试常见密码。只要有一个用户用了弱密码（如123456），就会被破解。而且攻击者可以通过响应提示判断哪些邮箱是有效的。

权限认证

问题描述

用户登录后，能访问哪些接口？能操作哪些数据？

垂直越权（Vertical Privilege Escalation）：

普通用户访问管理员接口，如删除帖子、封禁账号等。如果接口只校验了"用户已登录"，没有校验"用户是否有管理员权限"，那普通用户就能执行管理员操作。

水平越权（Horizontal Privilege Escalation）：

用户A操作了用户B的资源，如查看/修改/删除B的帖子。如果接口只校验了"用户已登录"，没有校验"资源是不是这个用户的"，那用户A只需传入用户B的资源ID，就能操作B的资源。

用户A登录后，调用 DELETE /api/v1/post/123（123是用户B的帖子）

如果后端只验证了Token，没有验证帖子123的所有者是否是用户A，

那用户B的帖子就被删除了，而用户B完全不知道是谁干的

方案对比

方案 思路 优点 缺点 我的评估
不校验 登录就能访问 实现简单 越权攻击毫无阻碍 不可接受
硬编码校验 每个方法写if判断 直观 代码重复，容易遗漏 维护成本太高
注解+AOP @RequirePermission声明式权限 代码清晰，自动拦截 需要学习AOP 我们选这个
Spring Security 用Spring Security全家桶 功能强大，标准化 学习曲线陡峭，配置复杂 太重了，不适合

我的选择理由：

  1. 注解+AOP最轻量：不需要引入Spring Security那么重的框架，用Spring AOP+自定义注解就能实现声明式权限控制。
  2. 权限逻辑与业务解耦：权限校验写在切面里，业务方法只关心业务逻辑，不会混在一起。
  3. 声明式权限：一行注解@RequirePermission(resource = POST, action = DELETE)就能声明接口需要什么权限，代码可读性强。
  4. 统一拦截：所有被注解标记的方法都会被AOP自动拦截，不需要手动写if判断。
  5. 如果用硬编码校验，每个方法都写if (!hasPermission(userId, "POST", "DELETE"))：代码重复率极高，新增接口容易忘记加权限检查，权限规则修改需要改很多地方，容易出错

如何防止越权访问？

问题描述

越权分两种：

  1. 垂直越权：普通用户执行了管理员才能执行的操作（如普通用户删除了别人的帖子）
  2. 水平越权：用户A访问了用户B的资源（如用户A通过修改postId参数，编辑了用户B的帖子）

垂直越权比较好防：判断用户角色即可。水平越权比较隐蔽：用户A有编辑帖子的权限，但他只能编辑自己的帖子，不能编辑别人的。

水平越权解决

PermissionChecker统一判断最合理：

PostPermissionChecker不仅判断"用户是否有删除帖子的权限"，还判断"这个帖子是否属于该用户"

审计监控日志

问题描述

安全事件发生后，怎么追溯和审计？

比如：某天管理员发现数据库里有一百条帖子被删除了。是谁删除的？什么时间删除的？从哪个IP删除的？删除了哪些帖子？是正常的操作还是攻击行为？

如果没有操作日志记录：无法追溯责任，不知道是谁干的；无法判断是系统bug还是用户恶意操作；无法向被删除帖子的用户解释；无法作为法律证据

有操作日志记录：精确知道是谁在什么时间从哪个IP删除了哪些帖子；如果该用户没有DELETE权限，说明是越权攻击；日志可以作为安全事件追溯的证据

方案对比

方案 思路 优点 缺点 我的评估
不记录 什么都不记 零开销 出事无法追溯 不可接受
手动记录 每个方法里写日志代码 灵活可控 代码重复，容易遗漏 维护成本太高
注解+AOP @OperationLog声明式记录 代码清晰，自动拦截 需要学习AOP 我们选这个

我的选择理由：

  1. 注解+AOP最轻量：用Spring AOP+自定义注解就能实现声明式日志记录。
  2. 日志与业务解耦：日志记录写在切面里，业务方法只关心业务逻辑。
  3. 声明式日志：一行注解@OperationLog(value = "删除帖子", entityName = "Post", operationType = "DELETE")就能声明日志规则。
  4. 自动记录：所有被注解标记的方法都会被AOP自动拦截，记录操作人、时间、耗时、参数、结果、IP等信息。
  5. 如果手动记录日志：每个方法都要写样板代码；新增接口容易忘记加日志；日志格式不统一，后期难以分析

监控规则设计

什么情况需要告警？

  1. 同一账号5次登录失败：记录警告日志

  2. 同一账号10次登录失败：锁定账户+发送告警邮件

  3. 同一IP大量登录尝试：记录警告日志

  4. 异地登录（IP地理位置异常）：发送安全通知邮件

  5. 敏感操作执行：记录操作日志

:::info 告警方式

  1. 日志记录（最基础）：所有事件都记录到OperationLog表

  2. 邮件通知（重要）：登录失败、异地登录、密码修改等

  3. 短信通知（紧急）：账户锁定、异常操作等

:::

Gateway认证的优势

  1. 统一入口：所有请求都必须经过Gateway，避免每个服务重复实现认证逻辑
  2. 性能好：Token验证在网关完成，无效请求不会到达业务服务，减少无用计算

第六阶段：遇到的问题以及应对措施

Q1: Token泄露了怎么办？

通过多层防护确保安全

  1. 短有效期：Access Token只有2小时，即使泄露窗口也很小
  2. 黑名单机制：用户发现异常可以立刻登出，Token即时失效
  3. 异常检测：如果同一Token短时间内从不同IP访问，触发安全告警
  4. 敏感操作二次验证：修改密码、删除账号等操作需要重新输入密码或短信验证

Q2: Refresh Token被盗用了怎么办？

Refresh Token比Access Token更危险（因为它能换取新的Access Token）。我的应对措施：

  1. 绑定设备指纹：Refresh Token创建时记录User-Agent + IP，刷新时校验
  2. 单点登录控制：新设备登录时使旧设备的Refresh Token失效
  3. 轮换机制：每次使用Refresh Token后，旧的立即失效，发放新的

Q3: 如何防范重放攻击（Replay Attack）？

****重放攻击是指攻击者截获合法请求后重复发送。我们的防范：

  1. Timestamp + Nonce：关键接口要求请求带时间戳和一次性随机数，服务端缓存已使用的Nonce
  2. HTTPS：加密传输，防止中间人截获
  3. 幂等性设计：POST/PUT接口使用幂等键（Idempotency Key），重复请求只生效一次

Q4: 如果要做第三方登录（微信/GitHub）怎么扩展？

A: 我们的架构预留了扩展空间：

  1. 引入OAuth2.0 Client：使用Spring Security OAuth2 Client或自行实现授权码流程
  2. 统一身份映射：第三方登录成功后，绑定或创建本地账号，再签发我们自己的JWT
  3. Token不变：对外仍然返回JWT双Token，内部认证流程不变

总结和心得

通过认证模块的安全设计与实现，我深刻理解了：

  1. 安全是系统工程：不是单一技术点，而是从传输层到业务层的多层纵深防御
  2. 攻防对抗思维：要从攻击者角度思考系统弱点，提前设防而非事后补救
  3. 平衡安全与体验：过度安全影响用户体验（如频繁验证码），需要在安全性和便利性间找平衡
  4. JWT不是银弹：JWT解决了无状态认证问题，但也带来了Token管理等新挑战
