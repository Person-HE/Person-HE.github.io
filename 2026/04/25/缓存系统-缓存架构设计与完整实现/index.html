缓存系统-缓存架构设计与完整实现

|浏览量:

从"为什么需要缓存"到"我的的项目中如何实现缓存的"的深度解析，包含完整代码架构设计

第一阶段：需求分析与技术选型

项目需求

我项目首页存在热门帖子，实时帖子展示两个功能，这里需要查询数据访问响应要快，而且请求量大，要减少对数据库的压力，还有对于一些高频访问的数据也要访问快一点，减少数据库的压力，对于那些需要跨实例共享的数据也需要缓存，保证多实例之间的数据一致

非功能要求：

  • 性能：L1缓存命中 < 1ms，L2缓存命中 < 5ms
  • 一致性：缓存与数据库数据保持一致
  • 可靠性：缓存击穿、穿透、雪崩防护
  • 可观测性：缓存命中率监控、慢查询检测

技术选型思考

缓存方案对比

方案 思路 优点 缺点 我的评估
单Redis缓存 所有数据存Redis 实现简单，支持分布式 网络开销大，热点数据访问慢 可用但不够
Caffeine本地缓存 单机内存缓存 极快（<1ms） 多实例数据不一致 适合热点数据
Caffeine + Redis多级缓存 本地+分布式两级缓存 兼顾速度和一致性 实现复杂 我们选这个

选择理由：

  1. L1本地缓存（Caffeine）：用户资料、圈子信息、热帖等高频访问数据放在本地内存，避免每次请求都访问Redis，减少网络开销。单机访问速度<1ms。
  2. L2分布式缓存（Redis）：Token、限流计数器、在线状态等需要跨实例共享的数据放在Redis，保证多实例间数据一致。
  3. 多级缓存架构：先查L1，未命中查L2，L2未命中查数据库并写回缓存。通过适配器模式统一L1和L2的访问接口，业务层无感知。
  4. 如果只用Redis，每次请求都要网络往返（即使Redis本机部署也需要TCP连接），而本地缓存直接内存访问，性能差距明显。

为什么缓存要分布在多个层次？

如果只用Redis做缓存，每次查询都要经过一次网络RTT（约1-5ms），热点数据频繁查询也是浪费。如果只用Caffeine本地缓存，多实例部署时数据不一致。所以缓存分布在两个层次：L1本地缓存负责极致速度，L2分布式缓存负责共享和一致性

第二阶段：多级缓存架构设计

缓存一致性方案对比

问题描述

数据库更新后，缓存中的数据就过期了。如何保证缓存和数据库的一致性？

方案对比

方案 思路 优点 缺点 我的评估
Cache-Aside 更新DB后删除缓存，下次查询时重新加载 实现简单，数据最终一致 并发更新可能导致短暂不一致 我们选这个
延迟双删 更新DB前删除缓存 → 更新DB → 延迟删除缓存 减少不一致窗口 实现复杂，延迟时间难确定 作为补充方案

我的选择理由：

  1. Cache-Aside作为基础方案：更新数据库后删除缓存，下次查询时自动从数据库加载最新数据。这是最简单可靠的方案，适用于大多数场景。
  2. 延迟双删作为补充：在高并发场景下，Cache-Aside可能出现"删除缓存后，旧数据又被加载到缓存"的情况。延迟双删通过第二次删除，清除可能被加载的旧数据。

核心实现详解

1. 多级缓存查询实现

架构设计思路：

  1. 门面模式（Facade）：CacheService作为门面，对外提供统一的缓存访问接口。内部委托给MultiLevelCache执行具体的多级缓存查询逻辑。
  2. 自动回源：当L1和L2缓存都未命中时，自动调用dbLoader.get()从数据库加载数据，并写入L2和L1缓存。业务层只需提供数据加载逻辑，无需关心缓存细节。
  3. 防击穿（分布式锁）：对于热点数据（如首页推荐帖子），多个请求同时查询缓存未命中时，如果没有锁保护，会导致大量请求打到数据库（缓存击穿）。使用Redis SETNX实现分布式锁，只有一个线程去数据库加载，其他线程等待后从缓存获取。
  4. 防雪崩（随机抖动）：如果大量缓存同时过期，会导致数据库瞬时压力激增。通过applyJitter()方法在过期时间上添加随机抖动（默认±20%），避免缓存集中过期。

2. 延迟双删实现

架构设计思路：

  1. Cache-Aside基础：更新数据库后删除缓存，下次查询时重新加载。
  2. 延迟双删补充：在高并发场景下，可能出现"线程A更新DB → 线程B查询旧数据写入缓存 → 线程A删除缓存"的情况。延迟双删通过第二次删除，清除线程B写入的旧缓存。
  3. 事务同步：如果更新操作在事务中执行，延迟删除任务注册到事务提交后执行，确保DB更新成功后才删除缓存。

关键代码流程：

3. 缓存预热实现

架构设计思路：

  1. 启动预热：系统启动时，加载热门数据到缓存，避免冷启动时大量请求打到数据库。
  2. 定时预热：每天凌晨3点（低峰期）重新预热热门数据，保证缓存数据新鲜度。
  3. 预热策略：只预热Top100圈子、Top200热帖等高频访问数据，避免全量预热占用过多内存。

4. 缓存监控实现

架构设计思路：

  1. Atomic计数器：使用AtomicLong记录L1命中次数、L2命中次数、DB查询次数、总耗时等指标。
  2. 命中率计算：命中率 = (L1命中次数 + L2命中次数) / (L1命中次数 + L2命中次数 + DB查询次数)
  3. 慢查询检测：DB查询耗时超过阈值（默认100ms）时，记录警告日志。
  4. 定期报告：每5分钟输出一次监控报告，包括命中率、平均耗时、慢查询次数等。

第四阶段：缓存适配器模式

为什么需要适配器？

问题描述

Redis支持多种数据结构（String、Hash、List、Set），但L1缓存（Caffeine）只能存简单的Key-Value。如何将不同的Redis数据结构统一映射到L1缓存？

为什么这样设计？

  1. 统一接口：无论Redis使用什么数据结构，业务层都通过相同的CacheAdapter接口访问缓存。
  2. 扁平化映射：Redis Hash结构有多个field，但L1缓存只能存Key-Value。通过redisKey:field的扁平化方式，将Hash的每个field映射为L1的一个独立Key。
  3. 可扩展：如果未来需要支持Redis List或Set，只需添加新的适配器实现，无需修改现有代码。

L3 DATA 数据层 帖子列表、评论分页 Redis 为主，较短过期 15分钟

第六阶段：缓存架构分层设计

总结

  1. 起初一开始我只是考虑到要保证性能高，访问快，同时对于请求量大的数据，要减少对数据库的访问压力，直接实现了多级缓存，但是我发现存在一堆业务service要使用多级缓存，Redis，我不可能在一个service中实现了缓存操作，在另一个service中再实现一遍
  2. 所以把这一套抽离成一个通用的方法，针对于各种不同的业务，只需要单独实现一个Mangaer类来实现具体的业务中使用缓存的操作，service中直接调用Manager类即可，进行了解耦
  3. 但是设计缓存时我发现有的是Hash，有的是String，而且使用多级缓存后，Caffiene没有办法直接存储hash结构的数据，所以需要特殊处理，所以我采用了适配器模式，针对于Redis的数据类型，把它们转化为Caffiene能存储的结构，便于多级缓存时，同一份数据在Caffiene能存储，在Redis中也能存储
  4. 但是后面又发现并不是所有的数据都需要多级缓存，有的只需要Redis，保证多实例之间数据一致且访问快就可以了（Token，在线状态，验证码等等），而有的就需要性能高一点，访问快一点（热门帖子，实时帖子）通过多级缓存实现正好满足，但是对于一些高频访问的数据，只要有Redis即可满足一定的需求了，并且各个数据之间的过期时间也可能不一样（根据业务需求有的过期时间长了数据太旧影响正常使用），所以又设计了四层缓存，每一层的缓存的配置根据业务和需求来自定义，这样就适配了各种业务，也不影响底层的通用方法
  5. 缓存不是银弹，是双刃剑。加了缓存能提升性能，但引入了数据一致性、缓存穿透、缓存雪崩、缓存击穿等新问题。每一个问题都需要单独设计防护策略。架构设计就是在做权衡：用复杂度换性能，用空间换时间。
  6. 多级缓存的本质是"分层防御"。L1 Caffeine挡掉最热点数据的访问（无网络延迟），L2 Redis挡掉大部分剩余访问（网络延迟但比数据库快100倍），数据库只处理缓存未命中的长尾请求。每一层都有自己的命中率目标，整体效果才是最优的。
  7. 缓存一致性的核心是"简单可靠"。最开始我想过很多复杂的同步方案（更新缓存、消息通知、版本号等），最后发现最简单的Cache-Aside模式（更新后删除缓存）反而是最可靠的。越简单的方案，越不容易出bug

这些设计保证了缓存系统的高性能，高可靠性，可观测性，可扩展性，维护性
