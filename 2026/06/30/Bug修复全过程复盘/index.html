不是炫耀"我修过这么多 bug"，恰恰相反——这些bug，每一条都是我的真实体会的经验。

字段映射：最让我脸红的 Bug 集群

字段映射的反思

把这三个 bug 摆在一起回头看——**病根都是"我以为"**。我以为驼峰会转，我以为加了字段就能用，我以为 Integer 装得下。任何技术框架的"默认值"都是双刃剑：MyBatis-Plus 给我自由，也给我陷阱。

AI 审核从未真正触发

这一组也最能体现我设计的 MQ + @Lazy 降级——RabbitMQ 异步队列是主链路，@Lazy 注入的同步审核是 fallback——但主链路本身的接口没接齐，降级再精妙也没用。

Bug 1：PostServiceImpl RabbitMQ 不可用时没 fallback

发帖流程是：用户发帖 → PostServiceImpl.createPost() → 发送 RabbitMQ 消息 → ContentAuditService 消费消息 → 审核。

问题是：我本地开发环境的 RabbitMQ 经常挂。一挂，发帖直接走不到审核。我压测时 RabbitMQ 正好挂了——所有帖子的审核流程都跳过了。

修复：给 ContentAuditService 加 @Lazy 注入到 PostServiceImpl，MQ 发送失败时直接同步调用审核：

Bug 2：CommentServiceImpl 评论根本不触发审核

修完发帖，我去看评论——评论压根没接入审核流程。我翻 CommentServiceImpl.createComment()，看完一整遍，没找到任何审核调用。

这是项目里最严重的一类 bug——"功能上线不等于功能可用"。PostServiceImpl 的审核我写了，CommentServiceImpl 我压根忘了写。修复：加 @Lazy ContentAuditService 注入，评论创建后直接同步调用审核。

反思

这一组 bug 教会我：功能上线不等于功能可用。一个流程有 5 个节点，其中 3 个节点"看起来对"、1 个节点是 TODO、1 个节点忘了接入，整体表现就是"审核功能有了"——但你一压测发现根本没人被审核过。

没有测试的代码就是这种状态：每一个节点单独看都"应该工作"，组合起来却完全跑不通。

MQ + @Lazy 的降级再精妙，忘了在评论里加 @Lazy ContentAuditService 注入就等于零。主链路必须先接通，再谈降级。

BeanUtils.copyProperties 的温柔陷阱

Bug 1：PostCreateDTO.images 静默消失

我做发帖功能时，DTO 里 images 字段是 List<String>（前端传多张图片），但 PostDetail 实体里 images 字段是 String（数据库存 JSON 字符串）。

我用了 BeanUtils.copyProperties(postCreateDTO, postDetail) 来转 DTO → Entity。

测的时候发现，前端传了 3 张图片，后端数据库里 images 列是空的。我加日志、加断点，盯了半小时——DTO 里 images 确实是 ["url1", "url2", "url3"]，但 Entity 里是 null。

BeanUtils.copyProperties 遇到类型不匹配时，静默跳过，不抛异常、不打日志。

修复：跳过 BeanUtils.copyProperties，手动 ObjectMapper 序列化：

这一节也最能体现我在项目里对 DTO/VO 类型一致性 的管理——DTO 的 List<String> 和 Entity 的 String 看起来"都是装图片的"，但语义完全不一样。类型一致性是契约，不是装饰。

反思

BeanUtils.copyProperties 是个好东西，但它会骗你。类型不匹配不报错、null 字段跳过不复制、嵌套对象不递归——这些规则如果不清楚，你以为的"代码简短优雅"实际上就是"埋雷"。

教训：以后任何用 BeanUtils.copyProperties 的地方，至少在第一次测试时加个断点验证。

文件上传的"路径不一致"小问题大影响

Bug 1：serveFile 端点的 /img/** 与上传返回的 /api/files/{fileKey} 对不上

这个 bug 特别有意思，因为它不是后端逻辑问题，是前后端契约问题。

FileController 里我写了两个端点：

上传返回的 URL 形如 https://example.com/api/files/{fileKey}。前端拿到这个 URL，渲染到 <img src> 标签里——404。

抓包一看：浏览器请求的是 https://example.com/api/files/abc123.png，但我后端只映射了 /img/**。URL 根本对不上。

修复：把 @GetMapping("/img/**") 改成 @GetMapping("/**")，让 URL 直接映射到存储路径。

反思

URL 是前后端的契约。

教训：写上传和访问的 URL 时，把它们写在一行。

上传：/api/files/upload，访问：/api/files/{key}

前后端两边的代码都按这个映射走，绝对不会错。

那些"修起来 2 分钟、找原因 2 小时"的 Bug

这一节是零散 bug 大杂烩，每一个都是"修起来快、找起来慢"。

Bug 1：分区管理创建按钮发送的字段名错了

前端 admin.ts 里 createSection 方法我这么写：

后端 SectionController.createSection 期待的是 contentType 字段，不是 sectionType。

我一开始以为是后端没接住——翻了一遍后端代码，确认 DTO 里是 contentType。然后翻前端代码——sectionType。字段名对不上。

修复：把前端 sectionType 改成 postType 和 sectionSubType 两个字段，分别对应后端的 contentType 和子类型。

Bug 2：头像 URL 404——Redis 缓存里还是老 URL

用户反馈"头像显示不出来"。我打开后台一看，avatar_url 列里写的是 https://example.com/static/old-avatar.png——这个域名我早就迁移了，新头像用的是 https://api.dicebear.com/...。

更新数据库里用户 1、用户 2 的 avatar_url 字段为 dicebear 的 URL，前端还是显示旧头像。

我第一反应："是不是缓存？" 一查 Redis，果然有这两个键：

里面存的是旧 URL。getUserProfile 这个 API 会先查 Redis，Redis 有就直接返回，不查数据库。

修复：清掉这两个 key，前端重新拉一次头像，新 URL 生效。

教训：任何"用户改了信息但显示没变"的 bug，第一反应是查缓存。Redis 这种"提速利器"在数据迁移时就是"同步绊脚石"。

写在最后

复盘完这几个 bug，我最大的感受是：bug 修复的时间主要花在"找原因"上。

真正写修复代码的时间加起来可能不到 2 小时；但"找到要改哪一行"加起来要花费很多时间。
