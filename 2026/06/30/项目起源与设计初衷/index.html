项目起源与设计初衷：致远 Flow 社区的来龙去脉

发表于2026-06-30|更新于2026-06-30|项目感悟
|浏览量:

我想用一篇博客的篇幅，把这个项目为什么立项、想解决什么问题、给谁用、我从中沉淀了哪些东西，原原本本讲给你听。是复盘。

写这篇博客，不是为了证明什么，是想把"我为什么做这个项目"、"我做了什么"、"我没做什么"讲清楚。一个项目最该被讲清楚的，从来不是技术名词，而是它背后的决定。

我为什么做这个项目

回头看，我之前其实写过不少练手项目——登录增删改查、表单管理、SSM 单体应用——全是简单的，没有价值的各种管理系统

真正让我下定决心的，不是"我又想写新项目"，而是"我意识到做过的项目撑不起一个真实后端工程师该有的厚度"。

从一个QQ频道开始，QQ有个频道功能，把所有的用户放在一个圈子里，用户们能在里面交流，后面在刷抖音的过程中，很多那些图文帖子，评论区里面有很多的真实评论交流，我发现因为算法，把所有的共同爱好，共同想法的用户们都集中到了一块，用户们之间真实的交流在共同一个圈子里，关键的点在于把用户们放在共同的圈子里，用户们之间的共鸣让用户能感受到“有人懂我”，“终于有真实的反馈了在我需要知道信息的圈子里”，而不是用户自己去寻找。

于是就有了 zhiyuan_Flow，也就是现在叫致远 Flow 社区这个东西，建立一个圈子，来帮助用户们在共同的圈子里真实交流。

我为什么选"社区"，不选"电商"或"博客"

这个问题我自己问过自己很多次。

答案其实很朴素：因为我真的在用社区。我刷各种技术社区、刷各种技术群——我比任何人都清楚一个内容社区的体验好在哪里、烂在哪里、哪一步让人想关掉 App。这是唯一一个我不需要去"研究用户"就能讲出大量细节的场景。

选社区不是因为我擅长社区，而是因为我对它最有体感，体感能让我在设计时少做很多拍脑袋的决定。

也正因为我自己就是用户，我从第一天起就知道几件事：

第一，圈子（Circle）必须是核心，不是帖子。一个没有"归属感"的内容平台，迟早会变成一锅粥；

第二，AI 审核必须有，因为开放 UGC 没有审核就是灾难；

第三，实时通知和私聊是留存命脉，没人愿意反复刷新去看有没有人回复自己。

这三条后来变成了我整个项目的骨架。

我想做什么样的产品

做这个项目的过程中，我反复问自己一个产品问题：致远 Flow 到底是给谁用的？

我最终给出的答案是：

给那群"想找一个比朋友圈严肃、比知乎垂直、比贴吧干净"的技术学习者用的垂直兴趣社区，他们愿意在一个圈子里深聊，他们对内容质量有要求。

给那些需要情感寄托，需要“有人懂我”的情感交流者，给他们提供一个有共鸣的圈子，保证圈子里每一个用户都有着共同的想法，有共鸣

给那些焦虑，有压力，无处释放的用户，一个释放的平台，匿名聊天，临时消息，过段时间消息就销毁

围绕着这群人，我把功能边界划得非常清楚：

进入致远 Flow 的用户，第一件事不是发帖，而是找圈子或者建圈子。所有的内容都归属于某个圈子，圈子再挂载到分区（Section），主分区有：聊天区，帖子区。分区是平台层面的，圈子是用户共建的。

还有一个点，灵感是来自于QQ频道，QQ频道有着严格的权限，而我选择不做。只有圈主，成员，因为从我作为一个用户的角度来看，很多人当了管理员会有很多的个人想法，从而导致整个圈子“变臭”，那怎么保证圈子正常运营下去？圈主能踢成员，AI审核来充当发表内容是否符合规范，这些机制能够保证圈子不会被有心之人”变臭“了

我做的第二个关键决定是所有互动都有反馈链路。点赞要推一条通知，评论要推一条通知，被圈主移除要推一条通知，公告要推一条通知。WebSocket 通道 + 数据库兜底 + 通知中心，是产品体验的底线。一个没有即时反馈的社区，用户很难有使用下去的心情。

第三个决定是AI 审核做兜底，而不是主审核。每个帖子和评论会先过规则审核（关键词、长度、频率），规则没把握的样本才会送到 AI 模型做二次判断。这套"规则 + AI"双层结构——AI 不是来当判官的，是来当"补漏员"的。

项目命名的故事

"致远 Flow"这个名字其实不是一开始就叫致远 Flow。

最早的项目名叫 community-platform，很工程师、很没灵魂。后来我想了几天，决定叫致远 Flow。

"致远"两个字的来源，是诸葛亮《诫子书》里那句"非淡泊无以明志，非宁静无以致远"。我承认这个名字有点中二，但放到一个社区上，它至少能传达一种"慢慢来、扎实走"的态度——和"水帖为王"的快流量社区做出区隔。

"Flow"则是我想强调的关键词。我希望这个平台上的信息是"流动"的，而不是"堆放"的。所以我后来做了排行榜、做了分享链接、做了首页热帖流——一切都是为了让好内容能从圈子里流到外面，而不是沉在某个角落等死。

做排行榜，为了给好内容一条"被看见"的出路。

至于英文名 zhiyuan_Flow，是因为我在 GitHub 上传代码需要一个能一眼认出来的项目名。致远的拼音直接拿来用，简单粗暴。

我设计的核心场景：用户的一天

我经常用"用户的一天"来检验自己做的功能是不是合理。下面这五个场景，是我目前觉得最能体现致远 Flow 价值的。

早上 9 点，张同学打开致远 Flow，首页推荐流是按最近时间热门的帖子。他点开一个关于"Redis 持久化"的帖子，看完顺手点了个点赞，点赞的动作会触发一条异步通知，送到作者王同学的通知中心。这一段涉及到Redis 缓存、消息队列异步解耦。

上午 11 点，张同学在自己加入的"Java 圈子"里发了一个求助帖。帖子发出去先走规则审核，过了；然后异步发到 MQ，等一下再用 AI 兜底审核。如果审核不通过，会进 AuditRecord 表，等用户申诉。这条链路里，MQ 异步、AI 兜底、审计可追溯三件套是我最满意的设计，老实说目前我只实现了审核记录，而没有实现申诉功能，因为平台后端管理系统还没有实现。

下午 2 点，王同学收到了张同学帖子下的第一条评论通知，是 WebSocket 推过来的。他点开通知直接跳到帖子详情，顺手用 WebSocket 回了句"我也在做这个项目，要不要私聊"。于是会话被建立。通知 → 帖子 → 私聊这个三段式跳转，是我自己用其他社区时最讨厌被卡住的地方，所以我一定要做顺。

晚上 8 点，张同学刷到圈子里有个帖子讲"分布式锁的三种实现"特别顶，他点了一下"分享"按钮，生成一个分享链接，可以发到用户来访问。

晚上 11 点，圈主在管理后台发了一条公告，公告通过 WebSocket 全员推送，所有在线用户的右上角会弹一个小红点。公告系统是很多社区会忽略的功能，但我做了，因为我自己做学习者社区时最讨厌"发了新规则没人知道"。

这个项目的技术亮点

接下来是这篇博客最有干货的部分，我把自己最满意的几个亮点列出来。

亮点 1：三级缓存做完了完整三防

"防穿透、防击穿、防雪崩"这三个词，几乎每一个讲 Redis 的项目都会提。

我在 MultiLevelCache 里把三件事做全了：

  • 防穿透用 NULL_PLACEHOLDER：当数据库里也查不到时，往缓存里塞一个特殊的占位符，TTL 短一点，避免每次都打到 DB。
  • 防击穿用 SETNX 分布式锁：同一个 key 同一时刻只允许一个线程去回源，其他线程在锁外自旋等待。
  • 防雪崩用 applyJitter：基础过期时间上叠加一个随机抖动，避免大量 key 同时过期把 DB 打挂。

亮点 2：AI 审核五层降级，兜底非常完整

AI 调外部接口这件事，不能假设它永远在线。我做的审核链路有五层：

  1. 规则审核：先跑关键词 + 长度 + 频率，这一步最快也最便宜。
  2. AI 模型审核：规则没把握的样本送给 ContentAuditService，调用 Langchain4j 的 ChatLanguageModel。
  3. 关键词兜底：AI 调用超时时回退到关键词二次扫描。
  4. 默认放行：所有自动手段都失败时，记一条 AuditRecord 让人工复审，避免漏杀优质内容。
  5. 熔断降级：AiCircuitBreaker 统计失败率，连续失败直接短路，短时间内不再调用 AI。

亮点 3：通知系统的"门面 + 策略 + 自动路由"三模式

通知系统最容易写成一坨 if-else type == "xxx"。

我用的是三段式：

  • 门面（NotificationPublisher）：业务侧只调用 publisher.publish(event)，不知道底下发生了什么。
  • **策略（6 个 **NotificationHandler）：每个 type 对应一个 Handler（Comment / Interaction / Message / Circle / Announcement / System），各自决定怎么拼装消息。
  • 自动路由（@PostConstruct）：所有 Handler 在容器启动时自动注册到路由器，业务不用关心有哪些 type。

加新通知类型只需要新增一个 Handler，零改动老代码。NotificationType 枚举里我登记了 14 种类型，覆盖了 post_comment / post_like / comment_like / circle_announcement / circle_join / private_message 等等。

亮点 4：权限策略模式 + 7 个 PermissionChecker

我最早用 if-else 写权限判断，写到第 6 个权限点的时候自己都看不懂了。后来重构成"注解 + 切面 + 策略模式 + 上下文"。

具体来说，7 个 PermissionChecker 实现类（CirclePermissionChecker、PostPermissionChecker、CommentPermissionChecker、SectionPermissionChecker、AnnouncementPermissionChecker、FilePermissionChecker，加上 PermissionChecker 接口和 PermissionContext 上下文）各自只关心自己那一类资源的权限。@RequirePermission 注解 + AOP 切面在 Controller 方法上做拦截，把当前用户、目标资源塞进 PermissionContext，让策略类自己判断。

这不是规则引擎，但是比 if-else 链好太多。新加一个资源类型，只需要新增一个 PermissionChecker 实现，业务代码零侵入。

亮点 5：MQ 4 大 Exchange + 死信队列

MQ 这一块我用的是 RabbitMQ，配了 4 大 Exchange：帖子事件、评论事件、审核事件、计数器同步事件。每个 Exchange 都挂了 DLX（死信交换机），消费失败的消息会进死信队列留底。

4 个 Consumer（PostNotificationConsumer / CommentNotificationConsumer / PostAuditConsumer / CounterSyncConsumer）各自只消费自己关心的那一份，互不干扰。

配合 application.yml 里的 publisher-confirm-type: correlated 和 publisher-returns: true，发布方可以拿到消息是否抵达的反馈。

亮点 6：JWT 双 Token + Redis 黑名单 + 白名单收紧

JWT 本身是无状态的，但无状态意味着"无法主动失效"。我用 access token + refresh token 双 Token，配合 Redis 黑名单解决：

  • access token 短期（2 小时），过期前可以静默续期；
  • refresh token 长期（7 天），用一次换一次；
  • 登出 / 改密时把 access token 塞进 Redis 黑名单（TokenManager.blacklist），TTL 等于 token 剩余生命周期。

特别值得讲的是白名单的"收紧"。JwtAuthenticationFilter 里的白名单原来很宽，/api/files/**、/api/ai/** 都放过去了。重构后只保留真正需要匿名的端点：登录、注册、刷新、公开列表、文件 GET 读取。AI 接口全部移出白名单，必须登录才能用。

TokenManager 整个类只有 3 个公开方法——storeToken / blacklist / isBlacklisted——把"有状态"这件事的边界划得清清楚楚。

亮点 7：AI 能力栈非常丰富

这一块是我"贪心"的地方，AI 相关的子系统我做了 6 个：

  • agent（CustomerServiceAgent）：基于 Langchain4j 的智能客服，带 Function Calling，能调 PostSearchTool / CircleSearchTool / FaqTool 这些工具。
  • audit（ContentAuditService + ContentAuditTool）：内容审核，上面讲过。
  • rag（RagKnowledgeService + DocumentIngestService）：知识库问答，支持文档切片入库。
  • memory（RedisBackedChatMemory + RedisChatMemoryStore）：把聊天记忆持久化到 Redis。
  • fallback（AiCircuitBreaker + AiFallbackService）：熔断和降级。
  • evaluation（AiEvaluationService + AiEvaluationRecord）：AI 输出的人工评价记录。

Langchain4j 版本是 1.0.0-beta3，6 个子系统都跑通，只是 AI 模型层接的是 MockChatLanguageModel。6 个子系统之间通过 AiConfig + AsyncConfig 统一装配。

亮点 8：多模块 Maven 架构 + 基础组件 + 运维

最后几个零碎的亮点我打包讲：

  • Maven 三模块依赖单向：models（DTO / VO / Entity）→ common（基础设施）→ api（业务）。依赖箭头只能从右往左，反向依赖编译期就过不去。这种约束让代码分层"物理上不可能乱"。
  • 雪花 ID + AES 文件存储 + BCrypt 密码：IdGenerator 是雪花算法生成的，AesUtil 给文件路径加密，BCrypt 处理密码，基础组件全部自己写，不依赖第三方奇怪工具。
  • 测试覆盖 5 个工具类：JwtUtilTest / AesUtilTest / DesensitizerTest / IdGeneratorTest / ValidationUtilsTest，加上 GlobalExceptionHandlerTest。Service 层覆盖率还不够高，但工具类做扎实了。
  • WebSocket 完整链路：ChatWebSocketHandler 收消息、SessionManager 管会话、MessageBroker 路由消息，离线和在线都覆盖。
  • 脱敏 + 校验 + 雪花 ID + CountDownLatch：Desensitizer 脱敏手机号邮箱，ValidationUtils 做参数校验，CountDownLatch 在并发场景下做协调——这些"小工具"是支撑业务不崩的真正基石。

我踩过的坑和推翻过的方案

这部分是这篇博客最值钱的部分。这些都是真实发生在 git 历史里的事情。

第一个坑是命名。 我最早把所有用户相关的表叫 User、UserInfo、UserExtend，后来改成 UserBase 和 UserProfile。这个改动看着小，但牵扯到十几张外键表的字段重命名，我前前后后改了好几天才落地。这件事教会我的是：早一点把命名约定定死，比早一点写代码重要。

第二个坑是 AI 审核同步阻塞。 第一版我让 AI 审核跑在发帖同步链路里，结果一打日志才发现，单条帖子延迟到了 1.2 秒。后来我把它改成：发帖先写库、再发 MQ 异步审核、审核结果回流到 AuditRecord 表。延迟直接降到 80ms 以内。这件事教会我的是：任何引入"第三方不确定性的调用"都不能进主链路。

第三个坑是权限策略膨胀。 我最早在service中用if-else 写权限判断，写到第 6 个权限点的时候service方法里面也越来越臃肿，也违反了单一职责原则。后来重构成"注解 + 切面 + 策略模式 + 上下文"，把 7 个 PermissionChecker 拆成独立类。这件事教会我的是：当你写第二个 if-else 的时候，就要开始想怎么拆了。

我还没做的事情

全文搜索我用的是 MySQL 的 LIKE，没有上 Elasticsearch。在我的项目规模下，LIKE 配合索引勉强够用，但我心里清楚，如果以后数据量真的起来了，LIKE 的天花板非常低。PostSearchService 和 CircleSearchService 我都写了，但底层就是 LIKE 加索引。

写在最后

**这个项目让我从一个"会写代码的人"，变成了一个"能讲清楚自己写过什么的人"**。这两者之间的差距，比我想象的还要大。

致远 Flow 这个名字取自"宁静以致远"。我希望能带着这个项目里学到的东西，走到下一段旅程里去。
