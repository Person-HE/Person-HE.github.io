1. JwtAuthenticationFilter：白名单收紧背后的克制

继续看 doFilterInternal 里的核心三步——tokenType 校验、黑名单校验、解析用户身份：

最后是 401 响应为什么手写 JSON、finally 块为什么必须清理 UserContext：

1.2 我为什么这么写

第一个纠结：白名单到底放什么

"按具体路径放"——/api/posts/hot、/api/circles/list 这种真正只读、不含个人数据的才放；/api/posts/{id} 这种虽然按理公开，但带状态（点赞数、是否已收藏），不归白名单管。

最让我头疼的是 /api/files/**。理论上文件读取应该是登录后才有权限（防止盗链），但前端首页 Banner 图、用户头像这些不能登录才看到。我的折中是：

只有 GET 方法走白名单——读头像可以匿名，但 POST（上传）、DELETE（删除）必须鉴权。这一个 && "GET".equalsIgnoreCase(method) 看起来不起眼，但它把"匿名读"和"写操作"彻底分开了。

第二个纠结：AI 接口要不要进白名单

早期 /api/ai/** 在白名单里——我想的是"AI 公开服务嘛，让大家都能体验"。

但后来我自己看监控时发现：AI 接口是重资源调用。如果不鉴权，恶意脚本可以无限刷我们的 token quota，甚至把整个 AI 服务拖垮。AI 鉴权不光是"权限"问题，是"防滥用"问题。

我的白名单哲学：宁紧勿松。白名单一旦放进去，所有人都会假设"这是公开的"，要拿出去非常麻烦。

所以默认不放，有充分理由才放。

第三个纠结：先校验 tokenType 还是先校验黑名单

代码里我是这样排序的：

为什么不先校验黑名单？

因为 refresh token 也可能在黑名单里（登出时一并失效）。如果先查黑名单，再判类型，那一次"用户拿 refresh token 调 API"的请求就会走到 Redis 才被拦下来——白白浪费一次 Redis 调用。

而且 refresh token 的特征很明显：它有 type=refresh 这个声明。我用 jwtUtil.getTokenType(token) 直接从 JWT payload 里读出来，不需要查 Redis。先做"零成本"判断，再做"有成本"判断，这是性能上最优的顺序。

校验顺序 = 性能顺序：从轻到重，从本地到远程，从声明到状态。

第四个纠结：401 响应为什么手写 JSON

为什么不用 ResponseEntity.status(401).body(...)？

因为 Filter 阶段还没有进入 Spring MVC 流程。在 OncePerRequestFilter 里抛异常或者 return ResponseEntity 都可能不走 ControllerAdvice。

我试过在 sendUnauthorized 里 throw new BusinessException，结果被 Spring Security 的 ExceptionTranslationFilter 接管，返回的是另一套 JSON 格式——前后端约定的一致性就崩了。

解决方案：在 Filter 阶段自己写 JSON。这虽然丑，但格式完全可控、与全局 Result<T> 保持一致。

写法也很克制：用 getWriter().write() 写裸 JSON，不引入 ObjectMapper、不引入 Jackson。

在 Filter 这种高频热路径上，能少一个依赖就少一个。

第五个纠结：finally { UserContext.clear() } 为什么必须写

UserContext 是基于 ThreadLocal 的，线程是会被 Tomcat 线程池复用的。

如果不显式 clear，下一个被分到这条线程的请求会读到上一个请求的 userId——这是非常经典的安全漏洞。

ThreadLocal** 永远是"用完必须清"**——这不是好习惯，是铁律。

2. TokenManager 3 方法：克制比功能多更重要

2.1 核心代码

TokenManager 的真实代码一共只有 3 个公开方法，是我改过最多次的类：

TOKEN_PREFIX 和 BLACKLIST_PREFIX 来自 JwtConstants，这是项目里"全局唯一的字符串集中地"。

2.2 我为什么这么写

第一次写：4 个方法的"全能 TokenManager"

我最早版本的 TokenManager 长这样（伪代码）：

看着挺完整，6 个方法。

但上线后我很快发现两个问题：

  1. **没人调用 **getTokenInfo。所有业务都直接通过 JWT 解析用户身份，根本不需要去 Redis 再查一次。
  2. refresh** 方法的实现到处都是坑**。到底是 refresh 整个 Token，还是只 refresh access？这两种语义在两个调用方那里不一致。

第二次改：砍到 3 个方法

我坐下来重新审视：

  • storeToken —— 必须有，登录时调用
  • blacklist —— 必须有，登出时调用
  • isBlacklisted —— 必须有，过滤器里要查

剩下的 getTokenInfo / refresh / deleteUserTokens 全部砍掉。

"想加"和"需要"是两回事。我曾经想加 validate 方法，结果发现 JwtAuthenticationFilter 里压根不需要这个——它只需要"是否在黑名单"这一个布尔。

storeToken 的设计：Hash 一次存两个 Token

为什么不存两次（put(TYPE_PREFIX + userId, access) 和 put(REFRESH_PREFIX + userId, refresh)）？

因为它们有共同的生命周期。access token 7 天过期，refresh token 也是 7 天过期。如果分开存，就要在两把 key 上分别设过期时间——任何一处忘了设，那把 key 就成了"永久 token"。

用 Hash 的好处：

  • 一把 key、一个 TTL，生命周期强一致
  • 取的时候 entries() 一次拿两个，减少 Redis 往返
  • 后续想加 deviceId / issuedAt 字段，直接 put 就行，key 不变

**Hash 结构的本质是"一组有共同生命周期的字段聚合"**。Token 是典型的"有共同 TTL 的成对数据"，用 Hash 是最自然的选择。

这是我重构这个类最大的收获：克制 > 完备。一个类最危险的时刻是它"看着什么都不缺"的时刻。

3.2 我为什么这么写

第一个纠结：为什么有 resourceIdParamName 和 relatedResourceIdParamName 两个参数

我最早的设计只有一个 resourceIdParamName。写完一个发帖接口，发现在一个"删除帖子评论"的场景下卡住了：

校验权限时只传了 commentId，可是"判断用户能否删除这条评论"需要先知道这条评论属于哪个帖子——帖子可能是私密的，评论可能在私密帖子下。

如果用户连帖子都看不到，他就不应该能删评论（防止"知道 ID 就能攻击"）。

所以我加上了 relatedResourceIdParamName：

切面会同时把 commentId 和 postId 传给 PermissionContext.check(...)，由对应的 CommentPermissionChecker 决定：先校验"用户能看 postId 这个帖子"，再校验"用户能删 commentId 这条评论"。

两个 ID 的语义不同：resourceId 是"要操作的目标"，relatedResourceId 是"上下文约束"。前者决定能不能做，后者决定有没有资格。

第二个纠结：为什么是字符串参数名而不是 Class<?>

我也想过这么写：

但 SpEL 有两个问题：

  2. 调试不友好。注解里写错一个字符，运行时才报错，而且报错信息很深。

我最终选择字符串参数名 + 反射。开发体验是：

字符串比表达式更直白。哪怕我以后想升级到 SpEL，注解的对外契约（resourceIdParamName = "..."）依然可以保持兼容。

第四个纠结：为什么用 @Around 而不是 @Before

用 @Around 是因为我要"权限不足时不执行原方法"。@Before 只能抛异常中断，但抛异常之后的处理（异常转换、状态码设置）会比较绕。

用 @Around 还能在 finally 里清理资源（虽然这里没有），更重要的是——未来如果我要在方法执行后做点事情（比如审计日志），@Around** 留了空间**。

用 @Around 不是为了复杂度，是为了扩展性。看似一样的两种切面，在"未来需求"面前天差地别。

7 个 Checker 怎么长出来的

不是一开始就 7 个。

第一次拆分——按"资源类型"切：PostPermissionChecker / CommentPermissionChecker / CirclePermissionChecker / UserPermissionChecker。这时候是 4 个。

第二次拆分是"加好友/发私信"这种用户间的关系权限太特殊了，从 UserPermissionChecker 拆出来，变成 FriendshipPermissionChecker、MessagePermissionChecker。

第三次拆分是文件资源的读写权限太特殊（只有 GET 匿名、其它要鉴权），单独搞了 FilePermissionChecker。

最终是 7 个：Circle / Post / Comment / Section / Announcement / File，加上被淘汰的 Friendship / Message / User 等。

拆分不是设计出来的，是业务逼出来的。我并没有一开始就"识别出"7 种类型——是代码越长越乱，最后我受不了了，才按"看起来不一样"的边界一刀一刀切。

第一个纠结：为什么用 List 注入而不是 Map

然后我在 @PostConstruct 里手动 for 循环构建 checkerMap——为什么不直接让 Spring 注入 Map<String, PermissionChecker>？

因为我踩过这个坑

Spring 的 Map<String, X> 注入，key 是 beanName，不是注解里的某个字段。

也就是说，如果我写：

那 checkerMap.get("post") 是拿不到的——key 会是 "postPermissionChecker" 这种完整类名小写。

用 List 注入 + 自己构建路由表虽然多 5 行代码，但key 是我自己控制的。

用 List 注入的代价：5 行 @PostConstruct 代码。
用 List 注入的收益：路由表 key 完全可控，调试时可以直接 checkerMap.get(POST)，而且支持日后从配置中心读取"哪些资源类型启用"等扩展。

第二个纠结：EnumMap 而不是 HashMap

ResourceType 是一个枚举，用 EnumMap 而不是 HashMap：

  • 性能更高（数组实现，O(1) 直接定位）
  • 不需要做 hashCode / equals
  • 编译器会检查 key 类型

这是 Java 集合的"小知识"，但用在合适的地方，能让代码既快又安全。

第三个纠结：找不到 Checker 时为什么返回 false 而不是抛异常

为什么不抛 IllegalStateException？

因为"找不到"是配置错误，不是用户错误。

我选择"返回 false + 打 ERROR 日志"——这意味着"用户没权限"。这种 fail-closed 策略在权限系统里非常重要：

权限系统必须 fail-closed。如果某天代码 bug 导致 checker 漏注册了，我希望用户无法访问，而不是所有人都能访问。后者是安全事故。

第二个纠结：defaultHandler 兜底

如果业务方传了一个 type="xxx"，而我们没有对应的 Handler，会发生什么？

用 defaultHandler 兜底 → SystemNotificationHandler，它会构建一个 "您有一条系统消息" 的通用通知

defaultHandler 是"系统弹性"的体现。如果某天新加一个 type="xxx"，但忘了注册 Handler，系统不会崩——用户至少能收到一条"系统消息"占位。比静默丢失好，比炸异常更好。

第三个纠结：5 个 Handler、2 个 Channel 怎么独立演化

我现在的 Handler 实现有 5 个：

  • InteractionNotificationHandler（处理 post_comment / comment_reply / post_like / comment_like）
  • CircleNotificationHandler（处理 circle_announcement / circle_join / circle_quit / circle_kick / circle_disband / circle_create）
  • AnnouncementNotificationHandler（处理 circle_announcement 关联逻辑）
  • MessageNotificationHandler（处理 private_message）
  • SystemNotificationHandler（默认兜底）

Channel 有 2 个：

  • DbPushChannel（写数据库）
  • WebSocketPushChannel（实时推送）

**Handler 关心的是"这条通知要长什么样"——title 怎么取、content 怎么拼、icon 用哪个。Channel 关心的是"这条通知怎么送出去"**——写库、推 WebSocket。

两者完全正交。我要加一种新的"点赞通知"，只需要加 Handler；我要加一种新的推送方式（比如短信），只需要加 Channel。互不影响。

第四个纠结：5 个 Handler 怎么独立演化

回到"5 个 Handler 独立演化"——5 个 Handler 独立存放在 5 个 .java 文件里，各自的修改互不影响。

我加一个 MentionNotificationHandler（@ 提及）只需要：

  1. 新建 MentionNotificationHandler implements NotificationHandler
  2. 在 getSupportedTypes() 返回 ["post_mention", "comment_mention"]
  3. @Component 注解

**零修改 **NotificationPublisherImpl。

这就是 @PostConstruct + 自声明 support 类型的好处：新增节点零侵入。

第一个纠结：为什么是 GET + DEL 而不是只 DEL

我第一次写的时候，释放锁是这样：

原因：分布式锁有"过期时间"。如果业务执行得慢，锁 10 秒过期自动释放了；另一个线程立刻抢到这把锁；这时我的 finally 跑到了，delete 删的是别人的锁。

教训：分布式锁释放必须原子。GET 校验 + DEL 删除，必须是 Redis 一次执行完成的，不能让业务代码分开做两步（因为中间可能被打断）。

Lua 脚本就是 Redis 提供的"原子事务"：在 Redis 单线程执行模型里，整个 if-GET-then-DEL 是不可分割的。

**释放锁的本质是"谁加的锁，谁才能删"**。token 就是"谁"的证明。

第二个纠结：token 为什么是 UUID 而不是线程 ID

我第一版用的是 Thread.currentThread().getId()——但线程 ID 会复用：线程死了，ID 留给下一个线程用。两个不同线程的锁可能 ID 相同。

UUID 是全局唯一的，重复概率可忽略。虽然 UUID 字符串比 long 大一点点，但 Redis 里 key 是字符串，value 多 36 字节不算什么。

安全 > 微优化。UUID 比 ThreadId 安全得多，那一丁点性能损耗完全值得。

第三个纠结：jitter 怎么算的

假设 jitterRatio = 0.1（代码里默认），expireSeconds = 3600：

  • 1.0 - 0.1 = 0.9（最小系数）
  • Math.random() * 0.2 给出 [0, 0.2) 的随机值
  • 总和是 [0.9, 1.1) 之间的随机数

也就是说，实际 TTL 在 3600 * 0.9 = 3240 到 3600 * 1.1 = 3960 秒之间均匀分布。

注：项目代码里默认 jitterRatio = 0.1，业务配置可以调整。我之前口述时把它说成 0.2（来自一些网络文章的通用做法），实际项目里跑的是 0.1——10% 抖动已经足够。

±10% 抖动为什么有效？

想象 1 万个 key 同时设置、TTL 相同 → 1 小时后同时过期 → 1 小时后瞬间打 DB（雪崩）。

加 ±10% 抖动后，过期时间被分散到 12 分钟的窗口里 → **DB 压力从"1 个尖峰"变成"一条平缓曲线"**。

**雪崩防护的本质是"打散"**。哪怕只打散 10%，对 DB 的冲击也会降到原来的几分之一。

第四个纠结：为什么是 StringRedisTemplate 而不是 RedisTemplate

我用了两个 Template：

  • RedisTemplate<String, Object> —— 用于业务数据（带 JDK 序列化）
  • StringRedisTemplate —— 用于锁和黑名单（纯字符串）

为什么不统一用 RedisTemplate？

因为锁和黑名单只需要 String。用 StringRedisTemplate 我不用考虑序列化方案；用 RedisTemplate 还要配 JdkSerializationRedisSerializer 或者 Jackson——业务数据的复杂序列化，污染了简单的锁数据。

不同场景用不同工具。

第五个纠结：延迟双删为什么挂 afterCommit

为什么不立即删除？

因为数据库事务可能回滚。如果我先删了缓存、然后 DB 写失败回滚，缓存里就是"假数据"——DB 没有那条更新，但缓存里是新值。

用 TransactionSynchronizationManager.registerSynchronization + afterCommit，能确保：

  • DB 事务真正提交后才动缓存——避免回滚导致脏缓存
  • 延迟 500ms 再删一次——覆盖"在我提交后、另一个事务读到旧缓存、写回新值"的窗口

缓存和 DB 的顺序不能反。
