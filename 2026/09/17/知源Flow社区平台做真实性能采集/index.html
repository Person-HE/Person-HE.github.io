第 1 部分 · 先把心智摆正：压测的数字只能证明三层里的两层

1.1｜压测到底在证明什么？我手上能产出的数据属于哪一层？

大多数初学者对压测的第一印象，是"跑出一个很高的 QPS 好写简历"。这个印象是错的，而且错得很致命，它把三层完全不同的事情混成了一层。evidence-pack/scripts/压测经验教训总结.md §0 给了一张三层表，我原样抄在这里：

层 问题 需要什么数据 知源 Flow 本机现状
1 机制 缓存/限流/熔断真的生效了吗？ 回源次数、命中率、拦截数、熔断次数 本机已可对账 ✅
2 尾延迟 高负载下用户会不会卡死？ P95 / P99，不是平均值 本机 A/B 已有 ✅
3 容量 能扛多少真实并发/QPS？ SLA-QPS（错误<0.1% 且 P99<300ms 的最大 RPS） 需云端/独立施压机，本项目没有 ✗

拿比喻把三层各说一遍：

  • 第 1 层（机制）像验证"涡轮到底装没装上"：不用上赛道，打开引擎盖看管路就知道。对应到软件这边：发一个请求，再发同一个请求，看 /actuator/cache-stats 里 dbQueryCount 有没有 +1，6.3 节有个 30 秒实验。
  • 第 2 层（尾延迟）像"高峰期收费站最慢的那 1% 车队堵不堵"：平均通过 4 秒不代表体验好，最慢的 1% 要是堵在 274 毫秒起步、抖动到 405 毫秒，那 1% 的人就在投诉。对应到数据：P95/P99 的 A/B 差值。
  • 第 3 层（容量）像"这条高速一共能过多少车"：必须把收费站搬到真实路况去测，在你家车库里推小车推出来的时速不算数。对应到实验：独立施压机 + 固定规格云主机上的 SLA-QPS 阶梯——本项目没做，所以全文一个字都不会吹容量。

这三层的边界感，是我自己觉得本文最重要的一件事。后面每一节出现数字，你都问自己一句：这是第几层的证据？

1.2｜为什么本机同机跑出的绝对 QPS 不能外推到生产？

evidence-pack/SUMMARY.md 第 3 行的环境声明原样抄出：

四个进程（被测应用、数据库、缓存、压测机）挤在同一台 Windows 上，意味着：

  1. 抢同一批 CPU 核。 压测越用力，JMeter 自己抢走的核越多，应用能用的越少，施压力度和被测性能互相残杀。所以"这台机器最大能跑多少"这种结论，都是这三个进程打架打出来的偶然结果。
  2. 抢同一块磁盘和同一份内存页缓存。 MySQL 的 InnoDB 缓冲池、应用的堆、JMeter 的采样缓冲，全在同一条内存总线上排队。
  3. 没有网络，这反而是把双刃剑。 同机走 127.0.0.1 回环，延迟近乎为零，RT 会偏乐观；CPU 互抢又让尾延迟偏悲观。两个方向的偏差搅在一起，得到的绝对数字不属于"理想生产"，也不属于"恶劣生产"，它什么都不属于。

反面教材本项目里就有一个：evidence-pack/matrix_post.csv 第 10 行，post_fixed_r200_rd2_170446 这一轮命中率 99.88%、只有 15 次回源，P99 却飙到 1386ms。缓存明明满血工作，尾延迟照样爆炸，因为那 40 秒里这台笔记本上发生了别的事（GC、磁盘刷盘、系统调度，具体根因未定位，【待你补充：该轮次对应的 GC 日志或进程级监控】）。同机数据的噪声底噪就是这么野。所以本项目对外的说法只有相对量，同一台机器、同一参数、只切一个开关的 A/B 差值，绝对 QPS 一个不外推。压测经验教训总结.md 第 12 坑原话："同机只报相对 A/B + 机制；绝对容量必须独立施压机 + 固定规格"。

1.3｜开环和闭环到底是什么？为什么我的主实验必须用开环？

闭环（closed-loop）：压测工具的一个线程发出请求 → 傻等回复 → 收到后才发下一条。比喻：拼车——上一车客人没到家，司机不发下一车。服务一变慢，每个线程等回复的时间就变长，发请求的手速跟着自然变慢。

开环（open-loop）：压测工具按固定速率硬发请求，不管上一条有没有回来。比喻：按时刻表发班车——到点就发，客人堵在门口也得发。服务变慢时请求不会变少，只会排队。

差别在哪儿才致命？看这个推演。原理出自 压测经验教训总结.md 第 1 坑，该坑的英文名叫 Coordinated Omission，协同遗漏：

时刻 真实世界发生的事 闭环压测器"看到"的事 开环压测器"看到"的事
第 1 秒 服务打了个 GC 嗝，卡住 2 秒 线程在等，没发请求 照发请求，它们开始排队
第 2 秒 恢复，积压排空 只记到"这 1 个请求 2 秒" 记到"这一批请求全在 2 秒+起步"
结论 — P99 被系统性低估：服务越慢，它测得越"不慢" 慢就是慢，如实记录

闭环最阴险的地方在这儿：服务变慢 → 自动少打 → 看起来 QPS 很稳、延迟也不炸。真实世界里的用户不会因为后端慢就少点按钮，所以闭环测出来的尾延迟是假的温和。evidence-pack/scripts/压测最终方案.md §1.4 的对照表把结论钉死了：本方案主场景只用开环（Constant Throughput 定时器），闭环不用。

知源 Flow 的主数据 evidence-pack/matrix_post.csv 就是开环产物——这也直接导致 9.2 节要讲的"开环实验里 QPS 没提升是正常现象"这一认知，两个知识点是一根绳上的。

1.4｜Constant Throughput Timer 的单位坑到底怎么坑人、怎么爬出来？

这是全文最需要醒目的一条坑：JMeter 的 Constant Throughput Timer（恒定吞吐量定时器）的单位是"每分钟样本数"（samples per minute），不是每秒。

事故现场（压测经验教训总结.md 第 2 坑原话整理）：想让压测器每秒打 50 个请求，于是填了 throughput=50，结果实际 QPS 只有 0.8。就这，我操。因为 50 个/分钟 = 0.83 个/秒。你以为你在压 50 RPS，其实你在压每小时三千个请求，测出来的延迟数字温和得像假数据。

换算公式只有一个：要压 N RPS，就填 N × 60。

目标 RPS -Jthroughput 该传 传错成"每秒"会怎样
50 3000 实测约 0.8 QPS，延迟假性极好
100 6000 实测约 1.7 QPS
200 12000 实测约 3.3 QPS

现象：直查版大量 500，被说成"缓存消灭了所有错误"。 真相：Hikari 默认 10 打满 → 连接超时 500；缓存只是少占连接。 正确做法：A/B 双方固定同一 Hikari（如 50），再对比。

Zipf 分布是什么、为什么必须用它？ 白话：真实社区里流量从来不均匀，热搜帖被几万人围观，冷门帖一天没人点。Zipf 就是"少数条目占大头流量"的数学形状。本项目的 ID 文件由 bench/ZipfGen.java（附-量化数据获取实战指南 §3.5 列的造数工具）按 Zipf 抽样生成：排头的少量热 ID 会被反复抽中，长尾冷 ID 偶尔出现一次。打个比方，食堂打饭窗口前，80% 的人挤在同 2 个窗口，其余窗口稀稀拉拉。

为什么这事对"命中率"数字影响巨大？缓存的容量有限，本项目 L1 热区只有 2000 个槽位。Zipf 把流量集中到少数 ID 上，热门 ID 全落进缓存，命中率自然就高。ID 要是均匀随机（每行等概率），80000 个 ID 轮流打，2000 槽位的 L1 根本装不下，命中率会暴跌。所以 7 部分那张表里 99.95% 这个数字，天生就属于"热数据场景"口径——9.1 节会把它作为局限主动披露，这里先埋钉。

本节归拢成一句：A/B 开关的正确形态，是让两组走同一份代码的两个分支，别搞两份代码。

4.3｜定时器在 jmx 里长什么样、calcMode=2 是什么意思？

jmx 第 24~27 行原文：

  • throughput 就是 1.4 节讲的每分钟样本数：${__P(throughput,50.0)} 接收命令行 -Jthroughput，脚本传的是 $Rps*60（如 100 RPS → 6000.0）。忘了 ×60，这里就退回默认 50/分钟≈0.83 QPS。单位和数值互相掩护，错得悄无声息。
  • calcMode=2 是作用域选择："This Thread Group only"（本线程组共享目标速率）。为什么重要？选成"per user"类模式的话，速率会被线程数一乘，300 线程 × 你以为的"目标值"= 灾难性的超发。本项目是单线程组，模式 2 表示"这 300 条线程加在一起每分钟共发 throughput 个"，正是开环恒定到达率的语义。
  • 定时器的工作方式是"该歇就歇"：线程算完上一条耗时后，定时器把它拖到节拍点才放行——所以请求的发起时刻由到达率表决定、不等上一条回复，这正是它把闭环改开环的机制。

想当场验证节拍，有个办法（附-量化数据获取实战指南 §3.2）：看 JMeter 控制台/日志的汇总行 summary = N in 00:00:40 = X/s，X 应≈目标 RPS。跑 100 RPS 看到 ≈100/s，这个定时器才算配对了。

4.8｜断言 3 到底怎么防"缓存串数据"？为什么它是多级缓存压测的生命线？

先讲事故模型。多级缓存最怕的一种 bug 不是"慢"，是张冠李戴：缓存 key 拼错（比如漏了后缀），异步回填写串，或者本地缓存被并发写坏，请求 /api/posts/1001 回来的是 1002 号帖子的 JSON。这种事故 HTTP 200、"code":200 双双达标，只有响应体的 id 会出卖它。压测不验 id，等于给一个"会把错误用户的数据发给别人"的系统发性能合格证，这比慢一万倍更糟。

断言 3 的实现（jmx 第 92~98 行原文）：

机制：每条样本发出时用的是哪个 ${postId}，回来的响应体里就必须含 "id":那个值。对不上，该样本 success=false，计入错误。100 RPS 档一轮约 3772 条样本（evidence-pack/matrix_post.csv 的 Samples 列），3772 次"点名答到"全对，Errors=0 才敢写进总表。SUMMARY.md §1 那行"错误（含 id 断言）0 | 0"，完整含义是：没报错，而且没串号。

写这条断言还有个类型小坑（第 7 坑）：别用 JMeter 的 JSON 断言去比 $.id，数字与字符串 "id":"6" vs "id":6 会给你"期望 66015 却 found 66015"的灵异现象。用 Contains 子串匹配 "id":${postId} 最稳。先 curl 看真实 JSON 形状，再写断言。

第 6 部分 · 命中率与回源数：应用记的账和 MySQL 记的账

6.1｜为什么说 JMeter 永远测不出"命中率"和"回源次数"？

一个初学者常见的误解：压测报告里应该什么数都有。**JMeter 只能站在门外看"多久回我、回的内容对不对"**，进程里发生了几次 HashMap 查找、数据库跑了几条 SQL，它看不见，压根没这个视角。所以：

数字 谁能测 怎么来的
P50/P95/P99、QPS、错误率 JMeter JTL 的 elapsed/success 列（5.5 节）
命中率、L1/L2 命中数、回源次数 只有应用自己 代码里手动埋点计数，走专门端点暴露（6.2 节）
全库 SELECT 总数 只有 MySQL 自己 全局状态计数器 Com_select（6.4 节）

这就是为什么本实验的"对账"需要三方数据源：JTL（门外）+ cache-stats（门内）+ Com_select（隔壁仓库门禁）。三方方向一致，机制结论才立得住；哪两方打架，先修账本，性能的事往后放——附-量化数据获取实战指南 §9.4 那个"baseline 的 DBQ=0 其实是没记账"的事故，就是账本自己打架的实例。

真实数据一对比就明白它们不是一回事（evidence-pack/matrix_post.csv 第 6~7 行，fixed/100 RPS 第 2、3 轮）：

回源 3 次，Com_select 却涨了 18820。3 次回源绝不可能产生 18820 条 SELECT——差的那一万八千条根本不是这个接口的回源发的。 那一万八千条往哪追？我只能列眼前看得见的：JMeter 3700+ 次请求每次都要过的鉴权链（JWT 解析后拉用户信息、登录态相关查询）、其它业务查询、心跳/巡检类 SQL——Com_select 是全库总账，dbQueryCount 是帖子详情回源的专项账（附-量化数据获取实战指南 §4.2 的完整解释）。

所以读数的时候有两条铁律，别嫌我啰嗦：

  1. 报"回源次数"这个具体数字，以 dbQueryCount 为准（它与你的回源逻辑 1:1）；ComSelectDelta 只当"应用没记错账"的外部旁证。本文主表里的 6267→3 全部是前者口径。
  2. 两本账只比方向，不做除法。 baseline→fixed 两本账同步下降（25073→18820、6267→3），方向一致说明缓存在起作用；拿 18820÷3 之类算任何"倍率"都是把两本不同单位的账混在一起算，纯错。

顺带一个口径彩蛋：fixed 组的 totalQueryCount 和 baseline 组的 dbQueryCount 都是 6267（6.7 节快照可见）——同轮请求触发的缓存引擎查询次数相同，只是这些查询在两组里分别落进"命中"和"回源"两个不同的抽屉。数字撞成一样不奇怪，本来就是同一批查询，只是记到了不同的科目下，谈不上什么彩蛋。

6.5｜为什么 fixed 组的 ComSelectDelta 也有 18820？它会不会暴露"缓存没用"？

新手看主表最容易产生的疑问：说好的缓存大杀四方，怎么 fixed 轮 ComSelectDelta=18820 看起来还是几万条 SELECT？两个原因（都能指到文件）：

  1. 固定开销不归缓存管。6.4 节说过，每条请求的鉴权链要查用户相关的表，这类 SELECT 和帖子详情缓存无关，压测窗口内 3772 个样本 × 若干条鉴权/上下文查询，轻松堆出上万条。baseline 的 25073 与 fixed 的 18820，差值部分（约 6 千多条）才近似"被缓存省掉的详情回源 SQL 族"——一次回源在 MySQL 侧是多条 SELECT 拼详情（组装帖子要拼作者、圈子、互动状态等，域12-④ 拆过 SQL 形状），1 次回源 ≠ 1 条 SELECT，这也是两本账不能相除的又一理由。
  2. 它反而是防伪证据。如果哪天你看到 fixed 轮 ComSelectDelta 掉到个位数，第一反应不该是狂喜，而是怀疑"这个接口是不是根本没查库/统计挂了"——一个活着的 Spring Boot 应用在同窗口里绝不可能全库零 SELECT。外部账存在的意义不在好看，在防自欺，它就只能干这一件事。

第 9 部分 · 局限与红线：哪些话打死不能说

9.1｜为什么 99.95% 命中率"只属于热场景"？四个成因逐个指认。

压测经验教训总结.md 第 10 坑把热轮命中率 99.8%~100% 被判"面试官觉得假"的原因列了四条，本文前面各节其实已经逐条埋过，这里集中指认：

9.2｜为什么开环 A/B 里没有"吞吐提升"这个指标？

看主表第一列数字就懂了（evidence-pack/matrix_post_median.csv）：fixed 三档 QPS=49.6/99.3/197.8，baseline 三档=49.7/99.2/198.1——两组 QPS 几乎一模一样。新手第一反应"缓存没提升吞吐？！"，实际上这是开环实验的定义使然（第 11 坑）：到达率被 Constant Throughput Timer 钉死成你的输入，完成吞吐≈目标值是实验有效的表现，不是缓存无效的表现。缓存的收益落在另外三列上：P99 骤降、DbQ 骤降，还有（若打满了）的错误率。

所以：

红线一句话（域17-⑤ §9 表下原话）：**"任何'提升了 X%'、'QPS 达到 Y'，本篇一个都没写。"** 本文同样一个没有。所有百分比差值（-97.8% 等）都挂在 P99/DbQ 的相对变化上，跟吞吐没关系。

9.3｜错误率 0 和 P99 里剔失败样本，这两处口径"亏心"吗？

有两件事得自己先交底，别等别人翻出来：

  1. 分位数只算成功样本（5.5 节 $_.success -eq 'true' 过滤）。附-量化数据获取实战指南 §4.3 教了标准话术："失败样本没算进分位数，所以 P99 好看一点点，但错误率我单独报了 0"——这叫主动交底。如果哪天错误率不是 0，这个口径就会系统性低估尾延迟（失败的请求往往是最慢的那批），必须把错误率和分位数绑着报。
  2. 错误率 0 是被设计的（7.7 节）：连接池钉死、MQ 摘除、单接口读压。换一个写多、依赖多的场景，0 就不再廉价。

再加一件没做的事：冷 ID 场景没测——"那需要混 10%~20% 冷 ID 重跑"（指南 Q7 答法，第 10 坑修法 2）。没做的实验自己先交代，同节原话管这个叫最高分的答法。
