知源 Flow 社区平台真实性能采集：多级缓存开环 A/B 量化

发表于2026-09-17|更新于2026-09-28|项目感悟
|浏览量:

这篇是给"缓存到底有没有用"这件事补的账。项目里三级缓存写了，简历上就能写"多级缓存优化"，但这句话没有任何人可以对质。我不想要这种数字，我想要的是别人问"你怎么证明"的时候，我能把原始文件甩过去的数字。所以做了这轮采集，方法一句话：同一份 jar，只切 cache.bypass 开关，JMeter 开环恒定吞吐，响应体断言，每档三轮取中位，应用埋点和 MySQL 状态两本账对账。主数据：帖子详情接口 100 RPS 下 P99 从 274ms 到 6ms，DB 回源每轮从 6267 次到 3 次。全部数字来自 evidence-pack/，当场可核。

先想清楚压测在证明什么，有三层

层 问题 要的数据 本机现状
1 机制 缓存、限流、熔断真的生效了吗 回源次数、命中率、拦截数、熔断计数 已对账
2 尾延迟 高负载下用户会不会卡死 P95、P99，不是平均值 本机 A/B 有
3 容量 能扛多少真实 QPS SLA-QPS（错误<0.1% 且 P99<300ms 的最大 RPS） 没做，要独立施压机

我的数字全部属于第一二层。第三层的数我没有，所以这篇里不会出现"支持多少并发"这种话。

闭环压测（线程池一直打）会把慢藏起来：服务变慢，线程回不来，发出请求自动变少，延迟就被低估了，这叫协调遗漏。真实用户不会因为你慢就不发下一个请求，所以主场景得开环恒定到达率。JMeter 的 Constant Throughput Timer 单位是每分钟，目标 100 RPS 要传 6000。我第一次不知道，填了个 100，跑出来 0.8 QPS，看报表还以为系统崩了，心里凉了一下。

环境，所有东西都在一台机器上

Windows 11 本机，16 逻辑核 15.19G 内存 JDK 17，应用（api-1.0.0.jar，-Xms1g -Xmx2g）、MySQL 8（库 zhiyuan）、Redis（压测固定用 db 2）、JMeter 5.6.3，全在同一台机器上互抢 CPU。这个前提决定了绝对值偏小、只能看相对量级，SUMMARY 头部自己写着"绝对 QPS 不外推"。

RabbitMQ 这轮显式关闭排除波动。Hikari A/B 双方固定 max=50、min-idle=10——这条是有前科的：上一轮连接池用的默认 10，baseline 一堆 500 错误，差点被我当成"缓存消灭了错误"的证据，其实压垮的是池子不是数据库。L1 压测参数 max-size=2000。MyBatis 关日志（NoLoggingImpl），不然日志 IO 自己就是瓶颈。

压测库的数据是造的，但造得讲道理：expand_data.sql 把圈子从 527 推到 500,527，成员 600 万+（每圈 12 个，按 (c.id*31+n*7919) mod 10052 映射到 10,052 个测试用户避唯一键），灌完 ANALYZE TABLE 让优化器选对索引。information_schema 直查：t_circle_base 约 50 万行，t_circle_member 约 257 万（当时快照），t_post_base 103,810，t_post_comment 399,572，t_post_interaction 992,631，t_user_base 9,993。帖子 ID 参数化文件 8 万行，用 Zipf 抽样生成，少数热帖被反复打、大量冷帖低频碰——100 个固定 ID 轮着打出来的命中率是假的，我不干。

实验设计

同一份 jar 两个模式，唯一自变量：

压测计划 bench/v3/jmx/post_detail.jmx：GET /api/posts/:postId，Header 带 Bearer token 和随机 XFF，CSV 数据源两个（post_ids.csv、tokens.csv，recycle），三条断言——HTTP 200、响应体含 "code":200、响应体含 "id":${postId}。第三条最关键：缓存如果串号返回了别人的帖子，HTTP 照样 200，只有把 postId 断回响应体才能抓出来。tokens.csv 是无 BOM 的，这也是翻车翻出来的，UTF-8 BOM 会让第一个 token 变成 \ufefftoken，全线 401，查这种问题查人半条命。

节奏：每档 Duration 40 秒、Warmup 15 秒、跑 3 轮取中位数（不是平均，baseline 三轮 P99 出过 6、405、274，平均数会把事糊掉）。run_post_ab.ps1 每轮干五件事：清空调用 /actuator/cache-stats/reset → 记 MySQL Com_select 起点 → 压 → 再取 cache-stats 和 Com_select → 解析 JTL 剔掉预热爬坡段和尾部两秒按下标取分位，追一行进 matrix_post.csv。

主结果，帖子详情 A/B 三轮中位

出处 evidence-pack/matrix_post_median.csv：

Mode RPS QPS P50 P95 P99 dbQuery/轮 Com_select delta 命中率 错误
fixed 50 49.6 5 6 7 353 9,425 99.97% 0
fixed 100 99.3 4 5 6 3 18,820 99.95% 0
fixed 200 197.8 4 6 19 30 37,058 99.76% 0
baseline 50 49.7 4 5 6 3,138 12,559 0% 0
baseline 100 99.2 4 68 274 6,267 25,073 0% 0
baseline 200 198.1 4 65 284 12,307 49,245 0% 0

三个细节值得说。开环下 QPS 不涨是对的，到达率被 Timer 钉死，fixed 和 baseline 的 QPS 都约等于目标值，A/B 比的是尾延迟和回源次数，"QPS 提升百分之多少"在开环口径下是伪命题。dbQuery 和 Com_select 是两个口径：前者是应用埋点数的帖子详情回源，后者是 MySQL 全库 SELECT 的增量，里面混着登录态用户信息那些固定开销，100 RPS 档 25073 对 18820，方向一致就行，不能当"帖子详情回源"读。命中率 99.95% 只属于热轮：Zipf 热点、预热和正式同会话、L1 压到 2000、期间没有失效写，四项加成叠出来的，生产不是这个形状，所以我只写"热场景命中率"。冷 ID 混测那一档，没做，不编。

配套的四组数

限流（fresh_ratelimit_20260916_185953.json）：固定同一个 XFF，60 连发 login，业务码 200 对 429 是 5 比 55，拦截率 91.7%，HTTP 错误 0——429 被包在 HTTP 200 的响应体里，JMeter 全绿不等于没被拦，判定必须看 "code":429。测限流必须固定 XFF（随机 IP 每次都是新窗口，测出来全是假成功）；反过来批量取 token、测 MQ 降级必须随机 XFF 加轮换 token，这两个方向相反的口径我都错过，前两轮 9/50、2/50 的"失败"撞的是用户维限流 10 次/60 秒，不是被测功能。

MQ 不可达降级（fresh_mq_20260916_190531.json）：RABBITMQ_ENABLED=false，50 个 token 轮换发帖，50/50 成功，avg 39.8ms，应用日志里有 Amqp 连接失败但主流程照样 200。它证明的是降级路径快，不等于开了 MQ 更快。

评论 SQL（fresh_explain_comment.txt）：联合索引 idx_post_create(post_id, create_time) 下 EXPLAIN type=ref rows≈50 无 filesort；无索引 type=ALL rows≈397,293；接口 n=30 实测 avg 28.5ms、P50 25、P95 35、P99 126。注意别把"397293→50"说成接口提速多少倍——那是两条不同 SQL 的执行计划对照，真正的收益是消掉 filesort。

LLM 熔断（matrix_fresh_aux.csv tag fresh_llm_191249）：故意配坏 Key 连打，前 5 次每次约 1575-1599ms（真调失败加退避重试加降级），第 6 次起熔断 OPEN，8-9ms，circuit/status 返回 failures=5 state=OPEN。要说清 8ms 不是"AI 优化到 8ms"，是跳闸不打了。

我给自己划的红线

SUMMARY 原文写着两条"不要写"：不要写 QPS 提升百分之几，不要写生产命中率 99.9%。这轮采集我还主动记了一笔不好看的账：fixed 第一轮 dbQuery 是 1290，冷启动回填的代价，第二三轮才降到 3——这个数我准备面试先自己讲出来，比被人从 csv 里翻出来强。并发矩阵那批（bench/matrix_final.csv，圈子详情闭环）QPS_MED 2172 到 2694，fixed 侧命中率 89.7 到 91.1%，但那是闭环、还带过 CPU 亲和性隔离，跟帖子详情这批纯同机不是一套手段，两批数拼在一起讲就是作弊，我不拼。

还有几个【无此数据】：整站混合场景（jmx 文件在，但矩阵不是它跑的）；SLA-QPS 容量；k6 只有脚本没结果。空着就是空着。

复跑

evidence-pack/scripts/README复跑.md：mvn -DskipTests package，备好两个无 BOM 的 csv，start_app.ps1 -Mode fixed 跑三轮，切 baseline 再跑三轮，看 matrix_post.csv 里的 P99 和 DbQueryCount，最小七分钟。EXPLAIN 五分钟不等压测，cache-stats 两次 curl 三十秒手测。复跑的目的是你自己测出自己的数，方向和量级对上就算成功，谁复跑谁别抄 274。
