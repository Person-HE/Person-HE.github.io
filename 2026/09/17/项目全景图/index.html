这是知源 Flow（Spring Boot 3.4.1 社区后端，分支 V3.0）的九张全景图。每张图管一个问题，图后面紧跟三段东西，逐节点说明，就是图里每个格子对应哪个真实类、真实文件；接线状态表，这条链路在什么条件下真跑、什么条件下不跑；还有关键源码，从仓库文件里逐字抄的，标了 路径:行号，你可以自己打开对着看。

逐节点说明：每个格子是哪个真实类

  • RequestTraceFilter：api/src/main/java/com/zhiyuanflow/config/RequestTraceFilter.java。它是全链路第一个执行的过滤器，类上标 @Order(Ordered.HIGHEST_PRECEDENCE)（该文件第 24 行）——这是全项目唯一显式声明了顺序的组件，给请求打 traceId 用。
  • JwtAuthenticationFilter：api/src/main/java/com/zhiyuanflow/config/JwtAuthenticationFilter.java。OncePerRequestFilter 子类，@Component 直接注册（Spring Boot 会把 Filter Bean 自动挂到主过滤器链上），负责"认证"这道闸：解析 Bearer token，把 userId/username 写进 UserContext（ThreadLocal）。图里那行"不查 Redis 黑名单"是真话，详见图3。
  • Controller 20 个：实测 grep -rl "@RestController" 命中 20 个文件——controller 包 13 个（Auth/User/Circle/Post/Comment/Section/Announcement/Message/Chat/Notification/File/Emotion/Behavior），ai 包 6 个（AiChat/AiCompanion/AiDiscover/AiDigest/CircleAi/Rag），外加 cache/monitor/CacheStatsController。
  • 三个切面：aspect 包下 RateLimitAspect、OperationLogAspect、PermissionAspect 三个 @Aspect 类。三者都**没有标 @Order**（实测 grep 全项目 @Order 只在 RequestTraceFilter 出现），也就是说同一个方法同时带 @RateLimit 和 @RequirePermission 时，谁先跑由 Spring 的默认顺序决定，代码层面没有承诺。这状态就是能跑，但没设计完。图里我按一组画的，没画成流水线，其实也串不起来。
  • Service → MultiLevelCache → Mapper：以帖子详情为例，调用链是 PostQuerySupportService.getPostData() → PostCacheManager.getPostDetail() → CacheService → MultiLevelCache.get()，回源 lambda 里才是 postMapper.getPostDataV3(...)。Mapper 27 个，实测 ls api/.../mapper | wc -l = 27。
  • MQ 组件：画在图里，但默认整体不装配。mq/config/RabbitMQConfig.java:13 和 4 个 consumer 类上都标着 @ConditionalOnProperty(prefix = "spring.rabbitmq", name = "enabled", havingValue = "true", matchIfMissing = false)，而 application.yml:41 给的是 enabled: ${RABBITMQ_ENABLED:false}。这条链的真实形态看图8。
  • WebSocket：websocket/ChatWebSocketHandler + websocket/SessionManager，在线表是**单机进程内的 ConcurrentHashMap**（SessionManager.java:29），看图9。
  • AI 纵队：ai/ 包全部代码，共 58 个 java 文件（实测 find ai -name '*.java' | wc -l），入口按域拆成 agent/companion/discover/digest/rag/audit。看图7。
  • 外部依赖四个：MySQL（application.yml:9，库名 zhiyuan）、Redis（application.yml:29-31）、RabbitMQ（application.yml:42-44）、LLM 网关（application.yml:117-121，Agnes AI 兼容 OpenAI 协议，模型名 agnes-2.5-flash）。

这条链什么时候真的跑？ 任何一次 HTTP 请求都跑前半段（Trace → Filter → Controller → 切面(如果方法有注解) → Service → Mapper → MySQL），这是主链路。走不走缓存取决于调的接口有没有接 CacheService（帖子详情/圈子详情/用户资料接了）；走不走 MQ 取决于 RABBITMQ_ENABLED（默认 false，且就算 true 也只是发帖路径有三处发送）；走不走 AI 取决于端点；WebSocket 只在 /ws/** 上跑，而 JwtAuthenticationFilter 对 /ws/** 是全放行（白名单第 53 行 "/ws/**"），WS 的鉴权在握手时由 handler 自己查 token。

这条链什么时候真的跑？

这张图没有运行时——它是编译期约束。依赖方向 api → common → models 是物理事实：把任何一行 import com.zhiyuanflow.dto... 反向加进 models，mvn compile 直接失败。这套架构不靠人自觉。分层靠什么，靠编译器，code review 那点人情帮不上。api 里也确实立了 ArchUnit（api/pom.xml:123-128，archunit-junit5 1.3.0，test scope），架构规则有测试兜底。

身份提取（ChatWebSocketHandler.java:342-383，节选）：userId 从 URL 路径 split("/") 取 parts[3]，token 从 query string 里手挑 token= 前缀，validateToken 再拿 jwtUtil.getUserIdFromToken(token) 和路径里的 userId 比对相等——路径写别人的 id、带自己的 token，过不去。三闸任一不过，分别 close(BAD_DATA / NOT_ACCEPTABLE)。

登记在 SessionManager.java:29,37-43，节选看下：

这个 put 是覆盖，也就是同一个 userId 底下只留最新那一根连接。域08-③ 205 的判定：要说这是设计好的"多端互踢"，算不上，就是"先能用后完善"那一套——旧端没有收到任何 kick/error 通知（全仓 session.close(...) 四个调用点全部在 afterConnectionEstablished 握手失败分支，不存在"因业务事件主动踢已建立连接"的入口，域08-⑥ 350）。手机和电脑同时登录，电脑后一连，手机就进入"连接显示正常、消息永不到达"的静默状态。

发送与推送（ChatWebSocketHandler.java:238-298 + MessageBroker.java:36-57）：私信先 privateMessageMapper.insert 落库，再 sendAndPush 通知（图6 那条链），接收者在线才 messageBroker.sendToUser。Broker 的推送是 CompletableFuture.runAsync 异步写帧：sendMessage 抛 IOException 时 log.error + removeSession(userId)——这个 remove 同样是按 key 删，不校验当前登记的是不是自己刚写失败的那根。域08-⑥ 251 还点了另一处，异步链不带结果消费，runAsync 里 try-catch 罩不住的异常，就是"把错误扔进井里"。

离线不补推：handlePrivateMessage 的离线分支只有一行 log.info("接收者不在线，私信已保存: receiverId={}", receiverId)（ChatWebSocketHandler.java:293-295）。接收者上线后靠前端主动拉 GET /api/messages/history/{userId} 补数据。这么选，需求那边是允许的，PRD 7.6 原文写"恢复后补拉 history 或依赖服务端补推（实现择一，验收保证不丢可见历史）"（域08-③ 66 行引用），本项目挑的是补拉这条路。含义也说穿："只要前端漏写那一次拉取，用户就会看到消息少了，而后端日志里全是'已保存'"。PRD 那边同时又规定发送必须走 WS、无 HTTP 兜底（功能清单 4.5 G-03，域08-② 49 行引用），可实测 REST 侧还留着 MessageController 的发送端点，live 状态，域08-⑥ 544 行判定它是"live 但语义偏离规范的残留入口"。用 REST 发的私信，接收者就算在线，实时推送收不到，红点也没有。

重连误删（这就是本图最疼的一格）：afterConnectionClosed（ChatWebSocketHandler.java:155-162）：

removeSession(userId) 只按 key 删。竞态时间线（域08-③ 334 逐帧版）：新连接握手成功 → addSession(B, 新) 覆盖登记 → 旧连接的 close 事件这时才到达 → removeSession(B) 删掉的是新连接 → 之后所有 isOnline(B) 恒 false，前端 onopen 正常、欢迎消息也收到了，然后进入永久静默。修法就一行，sessions.remove(userId, session)，两参值匹配才删，ConcurrentHashMap 本来就有这个重载。只是当时没人想到"同一个 userId 两根管子同时存在"的时刻。

集群即失联：sessions 是堆内对象，进程间不共享。域08-⑥ 382 原话：*"这一句决定了本域当前不可水平扩容——不是'性能不好'，是功能会错"*。更细的账在 398：双端登录分别落在实例1/实例2，两个 Map 各存一份，都收得到，看着比单机互踢还"爽"。代价是没有单一真相源，同一个用户在不在线，得看负载均衡怎么放你这根连接。部署那边也能对上：deploy 里的 nginx 配置 upstream zhiyuan_app 就 server app:8080; 一条，keepalive 没有，ip_hash 也没有（域08-⑤ 39 行实测登记）。

心跳：客户端发 heartbeat/ping，服务端回 pong（ChatWebSocketHandler.java:324-334）——就是应用层一个 echo。服务端不主动探活，也没有定时器去清死会话，一根会话死了，得等下一次往里写、写失败，才知道它死了。
