项目全景图：9 张图看懂知源 Flow

发表于2026-09-17|更新于2026-09-28|项目感悟
|浏览量:

这一版把九张图全部重画了。旧图里有几处画的是"我希望它长这样"，比如缓存图里我画了 Lua 原子释放锁，翻源码才发现释放就是一个裸 delete，哪来的 Lua。图这种东西最容易骗人，因为画完就没人再对一遍。所以这次每张图底下都标了哪些格子是好的、哪些是坏的，坏的用注释写在图里。

一句话：请求先过 Filter（认证闸），进 Controller 穿过三个切面，Service 在缓存、MQ、WS、AI 之间调度。没有网关层，早删了，那玩意一共就活了三十七天。

这里有个图上看不到但必须说的洞：登出后 token 写进 Redis 黑名单，但过滤器不查黑名单，所以"吊销"只做了一半，剩余有效期内 token 照样能用。旧图我在 Filter 那一格写了"+ 黑名单"，那是我以为，源码里 0 命中。

4. 权限策略路由，6 个 Checker

flowchart TD
    C["方法上的 RequirePermission 注解"]
    A["PermissionAspect 反射取参数"]
    P["PermissionContext
注入 List 再自建 EnumMap
key 自己说了算"]
    CK1["CirclePermissionChecker"]
    CK2["PostPermissionChecker"]

    CK4["SectionPermissionChecker"]
    CK5["AnnouncementPermissionChecker"]
    CK6["FilePermissionChecker
注册了, 但永远收不到请求, 死代码"]
    FC["fail-closed: 查不到 checker 直接拒绝"]

    C --> A --> P
    P --> CK1
    P --> CK2
    P --> CK3
    P --> CK4
    P --> CK5
    P --> CK6
    P --> FC

为什么注入 List 不注入 Map：吃过亏。通知系统那次 Map<String, Handler> 注入，key 是 Bean 名不是我给的业务类型码，路由全线失效还不报错。现在这张图这么画，就是那次先撞过。

FilePermissionChecker 为什么是死的：deleteFile 的注解把资源类型写成了 POST，请求全被路由到 PostPermissionChecker，拿文件 id 去帖子表查归属，谁的帖子 id 恰好撞上文件 id 谁就能删别人的文件。注册表里的格子存在，不等于有请求走得到。

5. 多级缓存读路径

flowchart TD
    Start["MultiLevelCache.get"]
    BY{"cache.bypass 开关?"}
    L1["L1 Caffeine"]
    L1H{"命中?"}
    L2["L2 Redis"]
    L2H{"命中?"}
    NP{"NULL 占位符?"}
    Lock["SETNX 抢锁, 值写死 1"]
    LS{"抢到?"}
    Wait["睡 50ms 回查 L2
还没有就自己查库"]
    L3["查 MySQL"]
    Has{"有值?"}
    PutNull["Redis 写 NULL 占位
TTL 取原 TTL 的一成, 下限 10 秒"]
    Put["写 Redis 加 jitter, 回写 L1"]
    Rel["releaseLock: 裸 delete
没有 token 没有校验, 可能删别人的锁"]

    Start --> BY
    BY -->|true 直查库| L3
    BY -->|false| L1
    L1 --> L1H
    L1H -->|hit 返回| R1["返回"]
    L1H -->|miss| L2
    L2 --> L2H
    L2H -->|hit| RB["回写 L1 返回"]
    L2H -->|miss| NP
    NP -->|是 返回 null| R2["返回 null"]
    NP -->|否| Lock
    Lock --> LS
    LS -->|失败| Wait
    LS -->|成功 锁内双重检查再回源| L3
    L3 --> Has
    Has -->|null| PutNull
    Has -->|有值| Put
    Put --> Rel
    PutNull --> Rel

三个防是真的：空值占位防穿透，锁防击穿，jitter 防雪崩。但 L1 不吃传入 TTL（所有 L1 条目用同一个过期），锁释放不校验持有者，这两个洞都在。100 RPS 下 P99 274ms 对 6ms、回源 6267 对 3，是本机同机 A/B 测的，数字在 evidence-pack/SUMMARY.md。

9. WebSocket 私信时序

sequenceDiagram
    participant B as 浏览器
    participant H as ChatWebSocketHandler
    participant S as SessionManager
    participant DB as MySQL

    B->>H: 连 ws chat 路径带 token
    H->>H: 校验 token
    H->>S: register userId 到单机 ConcurrentHashMap
    H-->>B: 握手成功
    B->>H: 发消息
    H->>DB: 落库
    H->>S: send 或 broadcast
    S-->>B: 推送
    Note over S: 扩容即失联, 会话只在单进程堆里
    B->>H: 断线重连
    H->>S: removeSession 只按 key 删
    Note over S: 旧连接关闭事件晚到, 会误删新连接登记

产品规矩是私信发送强制走 WS，禁止 HTTP 兜底发送，这条写在需求 7.6 里，理由是静默降级会把故障从可见变成不可见。技术上在线表就是个 HashMap 级别的单机真相，多端互踢和重连误删都还活着。

最后

九张图，每张都比旧版少画了一点功劳、多标了一点窟窿。全景图这玩意儿在我这儿翻过车，仓库里那套 docs/全景图 登记过三个网关类，源码里早删干净了，文档跑在代码前面，然后又跑丢了。所以现在图只当导航用，里面每句话都得能被源码驳回。驳回就驳回，源码赢是天经地义的，我自己都不接受这一条的话，别的就更没什么好讲的了。
