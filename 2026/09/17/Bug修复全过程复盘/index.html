开篇：一个 bug 到底该怎么复盘

攒了一批 bug 复盘放在这一篇，知源 Flow，Spring Boot 3.4.1 的社区后端。写法固定成七个字段，每条 bug 都按这个顺序走完，中间不留空洞：

字段 回答什么问题 小白为什么要看这个
现象 用户 / 接口 / 数据库分别表现出什么 先学会"描述问题"，不要一上来就描述代码
定位 我用了什么命令、看了哪些文件才找到它 排查手法比结论更值钱
根因 去掉所有表象之后，那一句话的原因 区分"这行写错了"和"我对框架的理解错了"
取舍 有几种修法，为什么不选另外几种 这一步最像工程师，也最容易被跳过
实现 真实 diff / 真实代码 看清"改到位"长什么样
复测 用什么证据说明它真的好了 会写测试不等于会验证
经验 这条 bug 教会我的、能搬到别的项目去的一句话 复盘的最终产物是可复用的判断

全文分三块。第一块是修掉的那批，主体落在一次提交里。第二块到今天还趴在源码里，每条都给 文件:行号 和当场跑出来的 grep 结果。第三块讲排查方法论，怎么从"用户说收不到通知"一路推到 Spring 的 Map 注入约定，怎么用 grep 判一段代码到底有没有人调，以及为什么修一个 bug 必须连带把同类问题一次查完。不想一件事修两遍，就这么简单。

读前三条约定

  1. 报错原文、代码、diff 全是从真实文件或 git show 输出里抄的，标了路径和行号，你可以逐条复核。
  2. 量化数字只有两个来源：git 统计（当场 --stat 实测）、evidence-pack/ 里的采集结果（标注文件名）。查不到的写【待你补充】，不猜。猜出来的数字我自己都不敢用。
  3. 不写"全部修完"。哪些是真没修、哪些是故意留的取舍，第二块单独立节说清楚。

"接口 200 + 表里没数据 + 日志有 error"，这个组合得留意。崩溃型的倒好办，这个是静默型：发送方法是 void，业务侧（点赞那个 Service）拿到的是正常返回，用户那边就是"我明明被人点赞了，小红点怎么不动"。功能刚上线就这样，挺丢脸的。

也就是说查表的 key 是 circle_create / post_comment 这种小写下划线串。那我当时的心理预期是，Map 的 key 应该就是各个 Handler 的 getSupportedType() 返回值。实测不是。打印 handlerMap.keySet()，打出来的是：

全是 beanName，类名首字母小写。handlerMap.get("post_comment") 永远 null，兜底那一句 handlerMap.get("system") 同样永远 null（真实 key 是 "systemNotificationHandler"）。于是 handler 带着 null 走进 for 循环，handler.shouldSend(...) 抛 NPE，再被循环里的 catch (Exception e) 一个接收者一个接收者地吞掉。就这么一路 null 到底，还得自己跑起来才看得见。

根因

一句话说就是 Spring 的 Map<String, T> 注入按 beanName 装 key，不看 T 上任何方法的返回值。

这是 @Autowired Map 的既定行为，不是我记错：

  • 注入 List<T> → 装所有实现，顺序由 @Order / 声明顺序决定；
  • 注入 Map<String, T> → value 是所有实现，key 是它们各自的 bean 名（默认就是类名首字母小写，除非 @Component("xxx") 显式命名）。

getSupportedType() 是我自己定义的普通 getter，Spring 根本不认识它。它想当路由键，就得自己建表。

还有一层，这个错误能全量活下来，是因为注释比代码可信。那句 Key: 通知类型码（如 "post", "circle" 等） 是写代码的人给自己留的假证据，我读到时完全没有要去验证的念头。往后注释里凡是出现"框架会替我做某件事"，一律当待验证项。

同仓库其实早就有一份正确写法摆在旁边，只是当时没人对照——api/src/main/java/com/zhiyuanflow/permission/PermissionContext.java 从 93fc60e 起就是这个形状：

注入 List、@PostConstruct 里按业务键自建 Map，权限域一直是这么写的。通知域抄都没抄对。

取舍

方案 做法 优点 代价 选不选
① 用 beanName 当 key handlerMap.get("interactionNotificationHandler") 零改动 业务类型码和类名绑死；一个 Handler 管多个类型时无法表达 否
② 给 Bean 显式命名 @Component("post_comment") 改动最小，保留 Map 注入 一个 Handler 只能挂一个名字，互动域要管 6 个类型码，做不到；且类型码写进 Bean 名，改名成本转移 否
③ 注入 List + @PostConstruct 自建路由表 见"实现" 一个 Handler 支持多个类型码；启动期能打印全表、发现冲突；与权限域写法统一 多一个初始化方法；丢掉 Spring 的 Map 语法糖 选它
④ 用枚举当 key（Map<NotificationType,X>） key 改成枚举 编译期安全，最干净 NotificationSendDTO.type 是 String，要改契约并波及所有生产方；本次是修 bug 不是重构 暂不做

选③的同时做了个小决定，接口从单数 getSupportedType() 改成复数 getSupportedTypes()。因为查完路由马上发现第二个问题，一个 Handler 天生要管好几个类型码（互动 Handler 管评论/点赞/拉踩 6 个码），单数签名从形状上就是错的。改接口会波及所有实现，好在只有 5 个且都在本域，一次改完的成本比留一个错形状低。

现象

还有一层只在"数据一致性"维度才看得见：修复选择的是"改代码去迁就数据（改成 1）"，但被改的那一方（种子数据）其实也认为自己是 2。 结果就是新代码 + 老库 = 圈主全体失权。这个组合在部署上会表现为"升级完应用忘了跑数据迁移"，而**仓库里没有任何一条 UPDATE t_circle_member SET role = 1 WHERE role = 2**——我 grep 过两份迁移脚本，只有那条会把角色写坏的语句（见下）。

  • 接线状态是类的一等属性，应该像单元测试一样被产出和维护。手记 §2 那张表是本项目唯一一次给全模块拍 X 光，它的格式值得固化：类 / 判定 / 判据 grep / 替代者。判定用词也定死三档，live（有调用点）/ unused（被引用但行为不生效）/ orphan（零引用），模糊的"好像没用"不入库。
  • 重构的完成定义要写成"旧路径消失"，不能写成"新类可以 new 了"。十行 RankingCacheManager 式类注释（"合并了原 X + Y 的职责"）就是重构走到一半的自首材料，看到这种句式，去 grep 原 X 原 Y 还活着几个，一查一个准。
  • 孤儿类的代价不该按 bug 数计，按"每个新读者被误导一次"计。它有完整类图、有 javadoc、有 Bean 注解，每个外观特征都在说"这是真码"。代码里从此有了两套叙事，读者先撞见哪套，哪套就成真了。
  • 零引用即零风险删除，这句算是给未来的自己立的行动准则。F13 全部条目里，除了 CacheResult（改造牵连签名）和"设计参考"论之外，找不出任何一个孤儿必须活着的理由。没理由就该删，删不动至少在类头写上 NOT WIRED，写不写另说。

G1 · 哪些是故意留的取舍，哪些是欠债：这两件事必须分开说

前面 F1 到 F13 列了十三条"还在"的问题。列问题容易，归类难。如果一个单干的人对着这十三条一律说"这是架构取舍，我考虑过"，那这一节就是公关稿。要是反过来全说"这是我没写完"，那就成检讨书了，检讨书我也不太会写。两种写法都学不到什么东西，因为都没去区分，就是这么回事。

这一节就一件事，给出一套能复核的判据，然后把 F1~F13 和几条不在 F 清单里、但同样常驻仓库的已知问题，逐条丢进两个格子里——取舍（算过账、写了代价，以及留了触发条件）或者欠债（没算过，没接线，改造成本还没摸清）。格子里放错一条，后面"如果只能改三条"跟着一起错，这个我也没辙。

先说清一件事，这一节不评价任何一条问题的严重程度。F5 的越权问题和 F11 的"无客流车站"问题，一个可能在真实流量下变成事故，一个在可预见的版本里都不会发作，但它们在这一节的分类完全可能一样——都是欠债。严重度决定改的顺序，类别决定你怎么对外说它，这是两条轴，我尽量不合并着讲，讲着讲着合没合我也说不准。

G1.1 先给判据：怎么区分"取舍"和"欠债"

三条判据，缺一条就降级为欠债

我把"这算不算一次取舍"拆成三个能核对的问题。顺序是有讲究的，第一条问意识，第二条问比较，第三条得看记录。一个人完全可能同时通过前两条但死在第三条上——心里真的权衡过，也真的比较过方案，但没留下任何字面记录，六个月后他自己都说不清当初为什么这么选。这时从外边看（包括从未来的自己那儿看），它跟欠债分不出来，那就只能按欠债处理。

判据 问的是什么 怎么在仓库里核对 通不过会怎样
① 知不知道 写的时候是否清楚这里"少做了什么"，还是压根没意识到 代码里有没有 TODO / 注释承认边界；issue 或提交信息里有没有出现过这个词；类注释有没有写出限制 这条叫"未知缺陷"，不属于本节两个格子中的任何一个，它是 F 清单本身的活
② 算没算过替代方案 是否至少写出过"另一种做法是什么，为什么这次不选它" 注释里有没有出现具体对方方案的名字（如 Redisson、Lua 脚本、MQ 广播、逻辑删除），而不是泛泛的"暂不优化" 这条叫"未验证的默认选择"，等价于"因为最省事"，归欠债
③ 有没有付出对价的记录 是否留下了为这个决定买单的痕迹：约束文档、部署要求、触发条件 部署文件里有没有把它钉住（如 compose 里显式写 false）；文档里有没有写"如果要上多实例，必须先改这里" 这条叫"隐性约定"，只有作者脑子里有，机器一重启就丢，归欠债

白话版：拿"租房子"来对齐这三条

术语先解释一遍，后面我就当它已经讲过了。

技术债（technical debt）：指为了让当前版本先跑起来，用一种"知道以后要还"的写法解决问题，代价是以后改起来更贵。比喻是贷款买房——先住进去，月供在后面等着。这一节说的"欠债"比这个词更窄一点，专指作者自己也没算过月供多少的那部分，所以它甚至算不上"有意识的技术债"，更接近"忘了自己还借了钱"。

取舍（trade-off）：在两个都能做的方案里，明确选了 A，并且写清楚"我放弃了 B 的什么，我用什么方式承担这个损失"。比喻是租房时选了离公司近但面积小的那套，并且在合同旁边贴了张纸写明"如果家里多一个人住，这个选择立刻作废，要换大的"。

用租房把这三条走一遍，走不走得出样子另说。

判据 取舍的样子 欠债的样子
① 知不知道 "我知道这房子隔音差" 住进去三个月才发现隔壁是酒吧
② 算没算过 "看过另外两套，一套贵 800 一套太远，都比这个差" "没看，就刷到这一套直接签了"

映射回代码，①对应"这个 Map 只能存本进程的会话"我知不知道，②对应"我有没有比较过 Redis 存会话 / 网关广播 / 消息总线，并且说出为什么这次不比"，③是 Dockerfile 里有没有一句话写明这个应用只能起一个副本。

一个反面用法：把"没做"说成"轻量级设计"

这一类措辞我在自己的提交信息里也写过。判据是语言的，当解释里出现"轻量""简洁""够用""项目规模小不需要"，而仓库里找不到对应的②或③的证据，那这就是欠债换了身衣服，叫法好听点而已。真正轻量的设计是有意识的产物，它通常会留下这类字：不做 X，因为 X 需要额外引入 Y 依赖；当前约束是 Z；触发条件是 W。少了 Z 和 W，剩下的就只能算修辞，我一般就这么判。

G1.4 最容易伪装成取舍的那三类欠债

前两节分完类，这一节讲为什么它会分错。"伪装"这个词不是修辞用的，它说的是一个真实的心理过程，作者确实觉得自己权衡过。人在被问到"这里为什么不做什么"时，大脑会现场编出一个合理理由，并把它归档成"当初我是这么想的"，六个月后这段记忆会显得完全可信。所以判据不能建立在"我是否记得自己想过"上，只能看仓库里能不能挖出记录，挖不出来就只能认。三类最常见的伪装，都对应一种"看起来像记录、其实不是"的东西。

伪装一 · 命名泄露意图：把"我想做"写成了"我在做"

形态：一个方法/类/常量的名字描述的是一个不存在的功能。本仓库的标本就是 decrementMemberCount（债6，CircleCacheManager.java:179-185），名字叫"减少"，实现是 +1，就这么直白。

名字说了什么 代码做了什么 谁被误导
"减少圈子成员计数"（含 Javadoc） cacheService.increment(key) 未来接"退圈"功能的人：他会以为这里已经处理好了，只在自己的调用点做 +1 的逆操作

为什么它容易伪装成取舍：当别人问"成员计数怎么没做减？"，回答"做了呀，有方法的"，这句话在当前时刻是真的，可惜是从名字读出来的，代码里没这句。这类问题的判定动作很便宜，对任何"名字暗示已完成"的方法，读一次方法体就行。名字里的动词和实现里的动词方向不一致，那它就不是取舍，是没写完还立了个牌子在那。

同一类的还有 TokenManager 的类注释（债3）：- 验证Token时检查Redis是否存在 描述的是一个不存在的功能。注释跟命名一样，是意图的化石，它记下作者当时想做什么，实际做成了什么它不管。这就是为什么 G1.1 的判据②要求的是"写出对方方案的名字"，愿望写多少都没用。

伪装二 · 只写不读：写入路径看起来像个功能

形态：数据被认真地写进某个存储，但没有任何地方读它。两个标本：

读侧：不存在（JwtAuthenticationFilter 中 grep TokenManager|RedisTemplate 零命中，当场实跑）。同一文件里的 storeToken（:36-43）更彻底，连写侧都没人调用。

A1 引爆的那个通知域，算这篇里做对了的那一半，C 系列的上传域就是反面，两面都摆，反面不藏。

正面这边：那次修复提交的标题写着"修复通知系统、AI审核、图片上传、帖子交互等14个核心bug"——通知域的 5 条（A1~A5），底下就 1 次事故，另外 4 条全是顺藤摸出来的。发现"路由全失效"之后，顺着同一条通知链路把写侧（A2 填错对象、A3 类型码大小写、A4 硬编码 sourceType）和读侧（A5 缺映射）一次过完——每条都有独立行号，没有一条是等用户第二次投诉才来的。藤就是链路：生产方 → 路由 → Handler 构建 → 落库 → convertToVO → 前端，六个站点挨个过一遍电。

反面同在这份账本里：C1~C3 修的也是链路（上传 → 校验 → 存储 → 落库 → 返回URL → 访问端点），但当时过的站点是"报障出现过的站点"。F4（FileStorageServiceImpl.java:38 调的校验器有洞）和 F5（同 Controller 里另一个端点注解挂错）都在 C2/C3 修完的同一批文件里躺着，扫描半径差一步。这就是 F 系列存在的实证理由：修一个 bug 的收尾，停在"这个 bug 好了"是不算完的，同一条链路上跟它同族的检查项得全部重新过一遍，这边就差那么一步。

落成三句问自己的话（每次修复收尾时问一遍）：

  1. 同链路：这条调用链上每个站点的同类逻辑，有没有同一写法？（E1 修注解参数字符串 → 该追问一句：全部注解的四个属性都核过吗？——F5 就是当初少问那一句留下来的。）
  2. 同机制：这个 bug 依赖的框架/中间件约定，项目里还有几处在赌同一个约定？（A1 赌"Map 注入 key 是业务码"→ 同项目 PermissionContext 的 EnumMap 路由就值得多看一眼——它做对了，Checker 自报 supportResourceType()；但 F5 摆在那，注册对不等于调用对。）
  3. 同产物：修复会不会生产新的观测失真？（A1 修完的 send() 循环带着 F9、A3 修完的 Handler 带着 F10——修复的 diff 也是新代码，是新代码就得跟新功能一样再过一遍评审，这一条我自己做得很糙。）

还有一层得算账：同类问题一起修，多花不了什么钱。排查 A2 的时候五个 Handler 已经全读过一遍了，顺手核类型码（A3）只多十分钟；分两次做，第二次的"重新进入状态"成本会翻倍，多出来的那部分就是给上下文切换交的税。

H4 · 七字段模板本身怎么用：每个字段的失败形态

复盘模板七个字段，前面 30 多节差不多是把它用满了。这里倒过来讲：每个字段最容易烂尾的样子，以及我自己用来查自己的那一句问话。

字段 烂尾形态（我踩过的） 自查问话 本文范例
现象 直接贴代码说"这里写错了" 不打开 IDE，我能把症状讲给一个不懂这个项目的人听吗？ F3："热度永远停在初始化时的样子"
定位 "看代码看出来的" 每一步有没有当场跑过的命令/断点/日志背书？ F12 的两条 grep 全文粘贴
根因 写成"手滑了""忘了" 去掉人称和情绪，还剩一句什么？ F9："定义漂移成'走完循环'"
取舍 整节空缺 空了就承认：当时只看到一条路 G1 表逐条定性取舍/欠债
实现 贴修复后的"理想代码" 贴的是 git show 里真实的那笔吗？未修的贴现状了吗？ F7 四段定点原文
复测 "手动试了一下好了" 有没有一条第三方 30 秒可复放的命令？ F2 的 grep 判定即封存章
经验 "以后要仔细" 这句话能搬进下一个项目吗？ F5："单点权限架构里一个枚举值写错=权限整体归零"

用的时候有三点，谈不上经验：

  • 七字段的顺序不能打乱。 先现象后定位，防的是"已经知道根因"那种心情倒推着走，把现象写成根因的形状——F4 如果先写根因，"现象"会被写成"WAV 通过了校验"这种结论式描述，"用户端是裂图"这层真症状就丢了。顺序能拦住的就这么一点，别的拦不住。
  • "取舍"为空 = 这条 bug 还没懂。 一个 bug 修完却答不出"另外两种修法为什么不行"，说明修的是症状，病没动：要么根因行写浅了，要么根本没修到根（本篇 B3 的"已修（病根在）"就是这么标出来的）。取舍这栏是七个字段里唯一往后看的，看的是"以后还能怎么修"，它逼着人承认有别解，而且多半是我不知道的别解。
  • 字段凑齐就是模板，模板也就是个顺手的家伙。 F 系列 13 条是"没修的 bug"也走七字段——现象（潜伏症状）、定位（grep 封存）、取舍（为什么不修）全都能填，只有"实现"合法地空着（写"当前源码=定位节引文，未修"）。往下说，模板不预设"修完"，"还在"才记进得了账本；"还在"那一半在面试里反而最能自证，它自证的是审核能力，跟运气不挨着。

H5 · 修完功能那一半，用执行计划验收另一半

慢 SQL 这类问题的证据怎么取，本篇在 F3 的实现节欠了一句"修好 WHERE 还要 EXPLAIN"，这笔账在这里补，补得也一般。真实材料是 evidence-pack/fresh_explain_comment.txt 的当场记录（评论链路，docs/sql 的联合索引 idx_post_create (post_id, create_time) 加上前后）：

这三段输出，按零基础的话读一遍：

EXPLAIN 字段 白话 这三条里的意思
type=ALL 全表扫，把书架整个拉出来翻 第三条：LIKE '%…%' 无法走索引，39.7 万行
type=ref 按索引直达一个值的分组 一、二条：post_id 定位没问题，rows≈50
Extra=Using filesort 取完还得额外排一次队 第二条：单列索引不含 create_time，排序白付一次
Extra=NULL 取出来就是有序 第一条：联合索引直接"按时间排好递给你"

同一条 SQL、同一个 post_id，只改索引形状，MySQL 的"体力活"就换了一档——这是"功能正确"之外的另一半：同一份正确结果，执行代价差三个数量级的时候，bug 只是还没发作成超时而已。 fresh_explain_comment.txt 头部注释"查询: WHERE post_id=? ORDER BY create_time ASC"，这份证据的采集姿势也就这样：先写下真实业务的那一条查询，再拿 EXPLAIN 问导航，对着手捏的玩具 SQL 做优化那就是自嗨。

缓存和接线的验收同理，用同一包里的另一份证据收个尾：evidence-pack/matrix_post_median.csv 的 A/B 设计——同一个 jar、只翻 cache.bypass 一个开关、每档 3 轮取中位（SUMMARY.md 开头的方法声明），100 RPS 档 baseline P99 274 ms 对 fixed 6 ms、每轮 DB 查询数 6267 对 3；200 RPS 档 P99 284 ms 对 19 ms、dbQuery 12307 对 30。写这些数字的规矩本篇一直守着：**数字只从采集文件来，文件名跟着标；绝对值不外推成生产结论，也不折算成"提升了百分之几的话术"**——它是同机压测，问的就一个："缓存这一层在本项目这个形状下值不值"，别的它回答不了。

五拍合起来我要的证据其实就三样：功能级的（结果对不对）、执行级的（代价大不大）、接线级的（这段代码今天真在跑吗），三样齐了才敢说一条 bug 的档案盖完。F3 只有前一半（WHERE 修好也没完，还得 EXPLAIN），F12 三样全缺（所以状态只能停在"还在"），F13 用第三样判了一个模块的生死。说是这么说，盖没盖完我自己拿不准，账本摊在这里，F12 还挂着没动，写到这也没劲再替它编一套说法了。
