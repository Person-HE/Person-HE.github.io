Bug 修复全过程复盘

发表于2026-09-17|更新于2026-09-28|项目感悟
|浏览量:

旧版这篇发布的时候，我以为是在复盘"我修过的 bug"。后来把整个仓库逐域读了一遍才意识到，这个叙述只覆盖了一半——另一半 bug 根本没被修，它们今天还在源码里活着，而且大部分活得很好。这篇重写版就按这两半讲。

那次修复：一条提交记录说 14 个，正文只列了 13 个

2026-06-28，提交 b183b68，标题是「fix: 修复通知系统、AI审核、图片上传、帖子交互等14个核心bug」。正文分四组列了 13 条，第 14 条其实是末尾那句「同时清理了未使用的gateway/services模块和文档文件」。数字口径本身就是个 bug，这个细节旧版我没敢写。那次提交的 stat 是 88 个文件，+803 行，-6643 行，删掉的比修掉的多了八倍。

四组 bug 挨个说。

通知系统是重灾区，五条连着一条链。NotificationPublisherImpl 里注入的是 Map<String, NotificationHandler>，我一直以为 Map 的 key 是业务类型码，其实 Spring 给的是 Bean 名，handlerMap.get("post_comment") 永远返回 null，所有通知在 if (handler == null) 那儿静默蒸发——不报错，只是永远收不到。测试时"所有通知都收不到了"就是这么来的。改成注入 List、@PostConstruct 里按每个 Handler 的 getSupportedTypes() 自建路由表之后，通知还是没来，因为第二个 bug 套在下面：setUserId 写反了，notification.setUserId(dto.getSenderId())，通知全发给了发起人自己。修完这个还有第三个：Handler 返回的类型码是大写 POST、ANNOUNCEMENT，前端约定是小写下划线 post_comment、circle_announcement，落库了但前端不认。第四个，InteractionNotificationHandler 里 setSourceType("CIRCLE") 硬编码，所有评论通知的来源永远是圈子，一级二级评论区分不出来。第五个，convertToVO 少了 relatedType 映射。这五个不是一个 bug，是一条故障链，任何一环单独修都修不干净。修到第三层我才搞明白，卡住我的不是 bug 有多难，是我根本一眼看不出那段代码在干嘛。

AI 审核四条。Mock 模型对审核请求回了一句散文而不是 JSON，下游解析器解析失败就判违规，正常内容被误杀——因为 AI 是假的，判定是真的，这个方向性错误我后来一直没修到根上，修的是给 Mock 加 "审核" && "json" 特判，测试永远绿，病根还在。handleViolation 高风险直接自动删帖补上了，RabbitMQ 不可用时 fallback 直接审核补上了，评论压根没接审核链路也补上了——最后这条是最严重的一类，功能存在不等于功能接线，CommentServiceImpl.createComment() 我翻一整遍，一个审核调用都没有，不是写错了，是忘了写。

图片上传三条。DTO 里 images 是 List<String>，实体里是 String，BeanUtils.copyProperties 碰到类型不匹配静默跳过，不抛异常不打日志，前端传三张图库里 images 是空的，我盯了半小时断点才找到。FileController 上传返回的 URL 和访问端点映射对不上，前端 img 404。UploadFile 实体里多了个 fileMd5 字段而表里没有这列，MyBatis-Plus 生成的 SQL 直接报错——这个和私信实体里的 readTime 是同一族错，字段是愿望，表才是现实。

帖子交互一条。PostInteractionResultVO 的 postId 和 userId 用的 Integer，雪花 ID 13 位，超出 Integer.MAX_VALUE 约四百万倍，新增点赞走了兼容路径没炸，取消点赞 intValue() 一转就溢出。改 Long 完事。

没修的那一半，今天还活着

这部分是逐行审计审出来的，全部当场 grep 复核过，我写这篇博客的此刻它们都在。

登出把 token 写进 Redis 黑名单，过滤器不查黑名单，"吊销"只做了一半；登录链路第 4 步检查用户状态整个被砍掉了，注释从 // 3. 直接跳到 // 5.，SQL 把封禁状态取到进程里然后当场扔掉，disabled@example.com 现在还能登录。

CircleCacheManager.decrementMemberCount，名字说减少，方法体是 cacheService.increment(key)，INCR 步长 +1。它至今没炸过，因为全仓没人调用它——一颗接上线就会响的哑弹，危险不在今天，在它的命名。

PostMapper.countWeeklyPostsByCircle 的注解 SQL，FROM 后面直接跟 AND，WHERE 整个不见了，MySQL 必报 1064；但它住在每小时定时任务里，外面套着 catch (Exception e) 只打一行 error 日志，接口不报错页面不报错单测不覆盖定时任务。结果就是热度刷新的唯一写入路径永远失败，广场地图上所有圈子的 heat 永远躺在 0.05 的地板上，"谁更热"被彻底抹平。一个永远不生效的功能，穿着一层永远不失败的错误处理。

SessionManager.removeSession 只按 key 删不校验 value，旧连接的关闭事件晚于新连接注册到达时，把新连接的登记删了，用户重连成功但从此收不到任何推送。修法一行，remove(key, value)，ConcurrentHashMap 本来就提供，只是当时没人想到同一个 userId 会有两根管子同时存在。

send() 循环里通道失败也照样 successCount+1；文件上传魔数校验只比前 4 字节，RIFF 是容器不是图片，一段 WAV 改名 .webp 五关全过，库里记着 image/webp，前端渲染成裂图；deleteFile 的权限注解资源类型配错，拿文件 id 去帖子表查归属，id 撞库就能删别人文件；删帖不动向量表，僵尸向量继续参与全表余弦、继续占 rerank 名额、继续花钱，然后回表时被静默丢弃，推荐列表少一张卡，日志一行都没有；AI 降级响应 success(true)，上层把它记成调用成功，熔断器的失败计数永远数不到"AI 其实没干活"，这是监控数据说谎级别的。

复盘复盘的是自己

早期还有两组丢人现在修掉了的：写分区时把 content_type 列想当然命名成 postType，Unknown column 'post_type' in 'field list' 糊在启动日志上；权限注解复制粘贴，createSection 的 action 忘了从 READ 改成 CREATE，圈主创建分区一直 403，我对着 AOP 代码看了半小时没发现问题，问题在注解外面。还有把用户改头像显示不出来的锅先甩给前端，其实 Redis 里 user:profile:1 存的还是旧 URL——"改了信息显示没变"，第一反应查缓存，这条现在还是我的肌肉记忆。

这些坑病根全是同一个三个字：我以为。我以为驼峰会自动转，我以为 Map 的 key 是我给的值，我以为 catch 住异常就是处理了异常。框架的默认值、注解的参数名、实体的字段，我以为的地方就是 bug 的藏身处。

而这次重写博客给我上的最后一课是：比"我以为代码是对的"更坑的，是"我以为 bug 修完了"。审查底稿里有一组数，4156 条路径引用，最后逐条回读排除 116 条假阳性、坐实 47 条真死链，根因就 5 个——连我自己用来防错的检查工具都要先被检查一遍。笔记里写"已验证"的那句话，也有过期的一天，网关都删了，旧笔记里还"验证过 gateway 起在 8080"。所以我现在只信一条规矩：源码赢，写文章之前，再去 grep 一次。
