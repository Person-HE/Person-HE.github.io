知源 Flow 项目总览与架构设计

发表于2026-09-17|更新于2026-09-28|项目感悟
|浏览量:

这篇重写了一遍。上一版是对着 README 写的，后来我把整个仓库从头逐行翻了一遍，切成十七个域，一个域六篇文档，翻完回头看旧文章，有几个说法是给自己脸上贴金的，没别的话讲。现在按真实的来。

这个项目是什么

知源 Flow 是一个社区后端，想法来自 QQ 频道，圈子、分区、发帖那一套。做到 V3.0 收敛成了别的样子：首页不是帖子列表，是情绪地图；帖子在这里叫心声，评论区叫共鸣墙，点赞旁边有个抱抱。核心链路是情绪地图进圈子，发心声，别人共鸣，抱抱和评论推通知，通知带私信，AI 陪伴和推荐挂在外面一圈做增益。

技术形态上它是 Spring Boot 3.4.1 的单体后端，Java 17，三个 Maven 模块。不是微服务。微服务那部分我真做过，后来整个删掉了，后面讲。

规模，给能复现的口径

简历上写规模最喜欢含糊，我这次不含糊，每个数都给统计命令，谁都可以自己去仓库数。

项 数 怎么数出来的
Maven 模块 3 个 models / common / api，依赖方向 api → common → models
Java 文件 399 个（api 238、models 120、common 41） find . -name "*.java" -not -path "*/target/*"
REST 控制器 20 个 grep @RestController 会命中 21 个文件，多那个是 GlobalExceptionHandler，它是 @RestControllerAdvice，子串误中
HTTP 端点 约 92 个 mapping 注解共 111 处，减掉 19 处类级 @RequestMapping，没细剔个别混用，所以说是约
实体类 30 个，其中 29 个带 @TableName ShareCode.java 没注解，写"31 张表"那种旧口径是我以前吹了，改
Mapper 27 个 api 的 mapper 目录数
SQL 脚本 12 个 deploy/tencent-lighthouse/sql/，01_base 到 99_local_seed

还有一个数想写：实战手记本身。十七个域乘以六篇，光 ① 类精讲每个域就 1892 到 6527 行。这个项目第一次有了比代码注释更了解代码的东西。

技术栈，以及里面没有的东西

有的这些：MyBatis-Plus 3.5.5 做 ORM；Caffeine 3.1.8 加 Redis（镜像 redis:7-alpine）加 MySQL 8 是三级缓存；RabbitMQ 走 AMQP，但是默认关着，RABBITMQ_ENABLED=false；JWT 用的 jjwt 0.12.3，access 加 refresh 双 token；AI 全家桶是 LangChain4j 1.0.0-beta3，本地还带了个 all-minilm-l6-v2 的 embedding 模型；BCrypt 在 spring-security-crypto 里，只用了加密这一个类。

没有的东西更值得说。

没有 API 网关。早期真有一个独立的 gateway 模块，AuthGlobalFilter、RateLimitFilter 那套，从第一条提交 2026-05-22 到 b183b68 删掉，活了三十七天。原因是只有一个服务的时候网关不是架构，是成本，白名单要存两份还会漂移。那些职责后来搬回了单体的 Filter 加三个 AOP 切面，删的时候我还不认，删完才认。

没有 Elasticsearch。全项目零 ES，搜索就是 MySQL 的 LIKE 加索引，我知道天花板在哪，先这样，反正暂时也没有更好的办法。

没有微服务。仓库里曾经还有过一个 services/ 目录，ai-service、auth-service 那几个 pom，同一次提交一起删的。

模块结构

三个模块，依赖单向，反向依赖编译期就过不去，分层想乱都乱不了。

models 是纯数据层，120 个 java 文件，entity 按业务分了 14 个子包，加 dto、vo、枚举、TreeNode。common 是基础设施层，统一 Result 信封、全局异常、JwtUtil、AesUtil、邮件、文件存储策略都在这。api 是业务层，controller 20 个，service、mapper 27 个，cache 包里 MultiLevelCache 在 core、各域 Manager 在 manager，aspect、annotation、permission，mq 包、websocket 包、notification 包（5 个 Handler 加 2 个 PushChannel），ai 包最大，agent、companion、audit、discover、digest、rag、fallback、memory 都在下面。

十七个域各留一句最疼的

我把仓库切成十七个域逐行读完后，每个域写了一句主线，贴在这儿。全是疼的，因为亮的那些旧文章里已经写过一遍了，看这份清单才知道剩下的。

域 一句话
01 认证与JWT双Token 黑名单只写不读、refresh 不轮换，"吊销"只做了一半
02 用户与资料 AesUtil.encrypt 零调用，解密接了加密没接，key 在 yml 里还是个大写 AES.KEY
03 圈子 decrementMemberCount 名字说减少，实际在执行 +1
04 帖子 热度刷新的 SQL 缺 WHERE，异常被 catch 吞了，圈热度永远躺在 0.05 的地板上
05 评论与互动 N+1 修了一半，头像那个循环没修完
06 公告 发布和置顶链路本身没大事，缓存失效跟着域12 一起疼
07 分区与审计 AgentRouter 的 case CONTENT_AUDIT 在，但 executeContentAudit 返回的是罐头文本
08 私信与WebSocket 所谓集群 Session 就是个单机 ConcurrentHashMap，扩容即失联
09 通知中心 send() 循环内逐人 try，通道失败也照样 successCount+1
10 文件存储 分享码五套实现四套是死的；WAV 改名 .webp 能过魔数校验，因为 RIFF 只比了前 4 字节
11 搜索与排行榜 零 Elasticsearch，共鸣榜是唯一活着的"排行榜"
12 缓存系统 三级读路径是真的，但 L1 不吃传入 TTL，锁释放没有持有者校验，延迟双删讲了没做全
13 权限系统 deleteFile 拿 POST 类型去校验 fileId，id 撞库就能水平越权
14 AI情感陪护 危机词号称三层实际生效 11 个，第二 turn 同步路径全表载向量做内存 cosine
15 AI推荐 删帖不动向量表，僵尸向量永久占坑；降级结果和正常结果共用一个缓存 key
16 AI-Agent路由 8 类路由只有 3 个 handler 接了线；降级响应 success(true)，把自己的熔断器清零
17 网关与MQ 网关活了 37 天整个删掉；Map 注入 key 是 Bean 名，路由失明过

这张表里没有一行形容词，每行都能指到一个类一个方法，想验的去仓库 grep，方法名都是真的。

部署

本地一条 docker-compose up：mysql:8.0、redis:7-alpine、rabbitmq:3-management、app 四个服务，应用镜像是多阶段构建出来的 api-1.0.0.jar，8080 端口。CACHE_BYPASS 环境变量留给压测 A/B 跳缓存用。云上有一套 deploy/tencent-lighthouse/，nginx 反代加 12 个初始化 SQL 加一堆 FIX 运维笔记，另有 aliyun 的一份 compose 和一个 render.yaml。README 里的安全约定：防火墙只开 8080，3306 和 6379 不对公网，JWT_SECRET、DB_PASSWORD、AES_KEY 一律环境变量注入，仓库不落真实密钥。

数字的规矩

所有量化数字只从 evidence-pack/ 来，主数据是 2026-09-16 本机重测的一轮：帖子详情 100 RPS 下 P99 274ms 降到 6ms，DB 回源每轮 6267 次降到 3 次。前提是 Windows 本机、应用和 MySQL 和 Redis 和 JMeter 同一台机器，绝对 QPS 不能外推生产容量，能外推的只有相对提升。这条规矩是被坑出来的，之前版本我写过"31 张表"，写的时候没数过，其实没这么多。

旧文章里我把自己写成"做完了完整三防"，现在看，三级缓存是真的在跑，"完整"两个字当不起，L1 的 TTL 就是个洞。这种话写出来就是给自己挖坑，面试一问就穿。
