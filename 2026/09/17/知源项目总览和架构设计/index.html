一、产品形态：这一节回答"它到底是个什么东西"

一句话：知源 Flow 是一个社区后端，Spring Boot 3.4.1 单体，Java 17，三个 Maven 模块，groupId 是 com.zhiyuanflow。微服务不是，网关没有，搜索引擎也没配。产品形态上它跟普通社区不太一样，不一样在哪儿我也讲不利索，就给代码证据吧，形容词省了。

1.1 首页不是帖子列表，是情绪地图

普通社区的首页，不就是帖子按时间或者热度排一排，排完就完了。这里的首页是一张地图，地图上的点是情绪。听着有点玄，往下看证据。证据一，情绪类型有枚举，全链路就这一个定义处，没有第二份。

10 种，就这 10 种。注意第 5、6 两个方法，业务规则其实压在它们身上：非法情绪不报错，"秘密"强制匿名。

证据二，看返回体。是个带坐标的节点集合，一个列表装不下地图这东西。

证据三，接口上挂着 60 次/分钟的限流。为什么单限它，因为它是首页，谁都进来看一眼。

这里有个点特别容易看漏。EmotionController **没有类级 @RequestMapping**，路径全写在方法上，一个方法一条。命令是 grep -rn "@RequestMapping(\"" api/src/main --include="*Controller.java"，数出来 20 个 @RestController 里头，有类级前缀的是 19 个，剩下那个第 20 个就是它。

5.1 为什么单独写一章"没有"

一个只有 389 个 Java 文件、92 个 HTTP 接口的单体后端，读者最容易产生的误解是"它应该有但我没看到"，"它少写了什么"倒是次要的。这一章的每一项都按同一个三段式来写，也没什么别的窍门：

  2. 判别命令：一条可以在你自己的终端跑完的 grep/find/git 命令，加它的实测输出。

七、统一响应信封与异常体系

7.1 先说人话：什么是"响应信封"

零基础的时候怎么写，Controller 里 return user;，前端就拿到一个裸对象，出错了呢，throw new RuntimeException("用户不存在") 一抛，前端拿到的是 Spring 默认那一坨白页 HTML，或者一段它自己都不认识的 JSON，字段名每次还不一样。这块也没什么好办法，前端同学只能写 if (res.xxx) 去判断成功还是失败，写一个接口猜一次，猜多了就烦。

"统一响应信封"就是把接口的返回都套进同一个壳子里，所有的，一个不落。壳子长什么样是固定的，前端只看壳子就够了，成功取 data，失败看 code 和 message，别的不用管。

这个壳子在知源 Flow 里放在 common 模块，路径就在下面。

五个字段，各自凭什么存在，我一个一个说，说的不一定都对：

还有个坑新手一般会踩，类里自己声明了 private final String message;，同时又调了 super(message)。@Getter 给这个字段生成 getMessage()，读的是子类字段，Throwable 本来也有 getMessage()，读的是父类存的那份。两个构造器都把同一个字符串同时喂给 super 和字段，两条路拿到的文本一样，就看不出问题。你要在别处只写了 super(msg) 忘了给字段赋值，@Getter 生成的方法就返回 null，这个编译器不管，只能自己留神。

顺序不确定会有什么看得见的差异？看 CircleController.java:102-104，同一个方法上三个注解的书写顺序是 @OperationLog → @RateLimit → @RequirePermission。书写顺序跟切面的执行顺序没关系，很多人以为排在前面的先跑，其实不是，Java 注解在 getAnnotations() 里返回的顺序不代表 AOP 织入顺序。

影响能看见的地方有两处，就这两处：

  1. 限流是否在鉴权之前：RateLimit 先执行的话，被限流的请求走不到权限校验，Redis 计数照常消耗。Permission 先执行的话，一个越权请求在耗权限查询之前不会被计数。两种都成立，就是审计口径不一样，哪种算数说不清。
  2. 操作日志会不会记录被拒的请求：OperationLogAspect 的 catch (Exception e) 会记一条"失败"日志。它排在最外层，限流和权限拒绝都能进日志，要是排在最内层，被限流挡掉的请求压根碰不到日志方法。

如果你要确定顺序，正确做法是显式加 @Order（例如鉴权 1、限流 2、日志 3），并在集成测试里断言。【当前切面执行顺序的实测断言：待你补充（仓库 src/test 下我未找到针对三切面顺序的测试用例）】

9.5 RABBITMQ_ENABLED：不是 Spring 标准属性，靠 yml 占位符接上

这里有个真实的坑，讲错了会被人挑出来：

  1. RABBITMQ_ENABLED 不是 Spring Boot 的标准环境变量。Boot 的宽松绑定（relaxed binding）认的是 SPRING_RABBITMQ_ENABLED → spring.rabbitmq.enabled；裸写 RABBITMQ_ENABLED 会被映射成 rabbitmq.enabled，那个键没人读。

11.4 三条红线：从踩坑文档里抄，不自己发明

evidence-pack/scripts/压测经验教训总结.md 列了 15 个坑，其中三条直接构成引用数字时的硬约束。

红线一 · 同机测出的绝对 QPS 不外推生产容量（坑 12，:165-168）：

现象：本机 2000+ QPS 写上简历，被问「几核几G」就崩。 正确做法：同机只报相对 A/B + 机制；绝对容量必须独立施压机 + 固定规格（如 2C2G）。

SUMMARY.md:3 的环境行就是把这条写在最显眼处：应用+MySQL+Redis+JMeter 同机。同机意味着施压进程和被测进程抢同一份 CPU/内存/网卡，测出来的"P99 6ms"里既没有网络往返也不代表真实部署的 contention。

红线二 · 开环实验不比吞吐（坑 11，:156-161）：

现象：fixed/baseline 的 QPS 都≈目标值。 原因：到达率被 Timer 钉死。 正确做法：开环 A/B 比 P99 / P95 / 回源次数 / 错误，不比吞吐。要吞吐能力：单独做 Stress 阶梯找 SLA-QPS。

去看数据就知道为什么：matrix_post_median.csv 里 baseline/200 的 QPS 是 198.1、fixed/200 是 197.8——两组吞吐几乎相等，因为它们是同一个 JMeter 定时器钉出来的。所以任何"QPS 提升 x%"在这个数据集上都没有立足点。

红线三 · 命中率只属于热场景（坑 10，:144-153）：

现象：热轮命中率 99.8%–100%，面试官觉得假。 原因：Zipf 热点集中 + 预热与正式同会话 + L1=2000 + 无失效写。 正确做法：1) 简历写「热场景命中率」，不写「生产命中率」 2) 混 10%–20% 冷 ID 3) 同时报 L1/L2/总命中 + dbQuery 4) 主动说局限

四个"原因"在本仓库都有对应实物：Zipf 生成器 bench/ZipfGen.java（3.1KB）与 bench/circle_ids_50k_zipf.csv（425KB）、bench/v3/post_ids.csv；L1=2000 是 start_app.ps1:47；"预热与正式同会话"是坑 14（:180-183）；无失效写指 A/B 场景只打 GET /api/posts/{postId}（SUMMARY.md:11），没有发帖/编辑去触发缓存失效。

现象：服务变慢 → 线程等响应 → 自动少发请求 → QPS 看起来稳、P99 也不炸。

12.3 哪几条最容易跑错

先说 jar 名字，真不能靠猜。它就是 api/pom.xml:14 的 artifactId 加上 parent 的 1.0.0 拼出来的，正确写法只有 api-1.0.0.jar 这一个，没别的；start_app.ps1:13 那边写的是 if (-not (Test-Path $jar)) { throw ... }。FIX_jar_name.md 那篇文档为啥存在？就是有人把 api-1.0.0.jar 直接传上服务器了，还指望 compose 认它。Redis 库号这块也是个变量，yml 写 database: 0（application.yml:32），压测时被 --spring.data.redis.database=2 盖掉，日常实例和压测实例的键空间就分家了，看 HitRate 之前不确认 -n，就会得出"缓存没用"这种错误结论，锅其实不在缓存。CSV 一律得是无 BOM 的，B15 那条命令就是为这个准备的。带 BOM 的时候 JMeter 的变量名会变成 \ufefftoken，看着是"带 token 的接口全 401"，手工 curl 又一切正常，特别容易被误判成鉴权 bug，只能说是玄学。A3 这类 grep 会漏掉 AES:，因为 yml 里那个键是大写开头（application.yml:104）。要核对顶层键，老实用 grep -n "^[A-Za-z]" 就行。B9 的 Com_select 是累计值，这个最容易顺手读错。得在稳态窗口前后各取一次再相减，直接读回来的大数字是全生命周期的，写进文章就是一句没法复核的话。最后这个，A21 和 A22 得搭着用，确认的是"3 轮中位"，明细 19 行里同一档可能出现两条 rd1（matrix_post.csv:2-3 就是两条 fixed_r50_rd1），你只按行数去除档数，轮次就数错了。容易跑错的大概就这些，别的坑，跑到了再说。
