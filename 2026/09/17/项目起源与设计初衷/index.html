一、这事儿是怎么开始的

1.1 起点不是"社区"，是 QQ 频道

我最早用的不是论坛，是 QQ 频道。 那东西结构特别简单，一个频道底下切若干个分区，分区里是一条一条的帖子，进频道先挑分区，挑完能看到别人发的，也能自己发，就这么三层，频道、分区、帖子。信息流没有，算法没有，页面也丑。但我那段时间天天打开，这个没什么道理讲。 后来我想为什么，肯定不是它做得好，它做得挺糙的。真实的原因就是我在那个频道里看到的人，跟别处看到的不一样，同一个频道同一个分区底下，大家在说同一类事情。内容吸引我是假的，人吸引我才是真的。分区这东西本身就是个筛子，把一类人筛到一块地方了。 那套结构我一直记着，等到自己做点东西的时候，拿它当底子抄了一遍，圈子等于频道，分区等于分区，帖子等于帖子。你现在库里看到的 t_circle_base、t_section、t_post_base 三张表就是这三层，一张不多一张不少。

1.2 真正的洞察只有一句话

抄结构是表面的事。频道那件事我得到的结论是另一句，把有共鸣的人放进同一个圈子，比把好看的内容排到前面重要得多。 这话听着有点虚，虚就虚吧，我拆开说它到底反对什么。 主流做法是内容优先，帖子打分、排序、推荐，谁刷到谁有缘，人和人之间没有稳定关系，就这一次曝光，产品形态就是无限下拉的信息流。 我想要的反过来，人先落地，内容只是证明我们是一类人的凭据。所以一条帖子值钱的地方不在它自己多好看，在它下面聚了谁。 这个结论直接定了几件后来很难改的事：

1.3 为什么做社区，不做电商也不做博客

这个选择我犹豫过，也没犹豫多久，理由特别不体面，我自己就是这类社区的用户。 我想了想自己每天会打开什么。购物网站排除了，那个我有明确目的才去。博客也排除，读的时候基本不互动，读完就走。会反复打开的，是那种不知道要看什么但就是想进去逛一圈的地方，QQ 频道、贴吧的某些吧、一些匿名树洞类的应用。共同点就一个，内容当不了主角，氛围才是主角。 挑选题我的标准就两条，有没有真实用户，有没有我自己。电商碰过两次，两次都卡在用户从哪来这一步，技术上没什么问题，流量问题，我一个人不可能有供给也没人有需求。博客太薄，业务面窄到没地方放工程复杂度，硬塞就是拿一个 CRUD 套一层壳。 社区这两条都占，我自己就是用户，我知道哪种交互会让人难受，同时业务面够宽，身份、内容、关系、消息、通知、文件、权限、实时、检索，天然十个以上的域。这个项目最后切了 17 个域，就是这么长出来的。

代价也说一句，很实在的，社区没有明确的商业闭环，所以我做的一切都得能用工程语言解释，不能拿"这是核心业务逻辑"糊过去。这么一看反倒是好事。

1.4 一开始就定下的三条判断

这三条是写第一行代码之前就记下来的，不是事后追认。后面每一节它们都会被兑现成具体的类和表，先原样放这儿。 判断一，圈子是核心实体，帖子只是圈子里的内容。 反过来说，别做那种帖子管理系统顺便有小组。两种做法在数据库上的区别，后者的 post 表里小组是可选字段，前者的 post 表里小组必填。我这儿必填，见 models/src/main/java/com/zhiyuanflow/entity/post/PostBase.java:42，circleId 注释写着 NOT NULL, INDEX，sectionId 在 PostBase.java:93，注释写可为 NULL，历史遗留，V3.0 在 service 层把它补成必填了。 判断二，只要开放 UGC 就必须有内容审核，而且必须有机器审核。 因为我没人工。独立开发者一个，几千条内容，靠眼睛看是不成立的，所以这条谈不上加分项，它是准入条件。审核这条的兑现见 §2.2，最后落成一个后端旁路服务加一张 t_audit_record 表。 判断三，实时通知和私聊是留存的命脉。 社区里最脆弱的时刻就是发完之后没人理。一个人认真写了三百字，两小时后还在等回复，等不到，就不会再写了。所以我要让回应能被立刻感知，哪怕就一条"你的帖子收到新的共鸣"。兑现见 §2.3，落点是 NotificationPublisherImpl 的双通道（DB 落库 + WebSocket 实时）和 /ws/private/{userId} 这个端点。 三条判断都不新，网上到处有人这么说，谁都会说。区别在于有没有变成代码里的硬约束，这个我后面一条一条查。

1.5 名字的来处

最早仓库叫 community-platform，直白，也很没用，只说了这是个什么东西，没说它想干什么。后来改成知源 Flow，"知其源、明其流"，取的是情绪从哪来、往哪去那层意思。改名的成本主要在包名，com.zhiyuanflow 这个前缀就是那次留下的，根 pom.xml:20 的 <description> 现在还是 Zhiyuan Flow Multi-Module Project，懒得动了。

3.5 匿名开关交出去：由分区决定，不由用户手选

这是我改得最舍不得、事后又最满意的一条。 改之前，发帖有个匿名复选框，想匿就匿。所有论坛都这么干。 为什么不行。我看了自己以前在别的地方的发帖行为，发现这个复选框的语义根本没被用户理解，它实际混着两件不同的事，一件是"我不想被认出来"，因为内容私密，一件是"我不想要身份带来的压力"，因为想说得直白点。 第二种人经常不勾，勾了感觉像"躲起来说话"，有点丢脸。结果就是分区语义和匿名开关互相打架，一个已经叫"匿名树洞"的分区，用户还能选实名发，一个公开分区，用户可以突然匿名。同一块墙上混着两种身份，读的人完全没法建立预期。 改成什么，匿名是分区的属性，帖子跟着它走。进匿名区就是匿名，没得选，进公开区就是实名，也没得选。用户要做的选择从"要不要匿名"变成"去哪个区"，后者是他在挑氛围，本来就在做。 字段确实在分区上：

5.2 私信强制走 WebSocket——以及这一条我其实没做到

先说我为什么要把这条写成铁律。 因为"能凑合"会毁掉体验的一致性。WS 断了就自动切 HTTP 发的话，用户看到的现象是：有时候消息秒到，有时候消息要刷新才到，有时候对方在线但你发出去像石沉大海。这三种都叫"成功"，所以没人报错，但用户会觉得这个产品忽快忽慢，不可信。HTTP 兜底把这个问题永久藏起来了，监控里全绿，用户体验里全在那儿。 所以契约是这么定的：

"禁止静默成功"这五个字是这条铁律的核心。宁可让用户看见一个红色横幅，也不能让他以为发出去了。 然后说没做到的那部分。这是目前实现里最不体面的一条。 代码里 POST /api/messages 是活的：

7.1 容量压测（SLA-QPS）没做，本机数据不能替它

这批 evidence-pack 的数据能回答"机制有没有生效""尾延迟改善了多少""扫描量降下来没有"。有一个问题它们回答不了：这个系统能扛多少并发。 方案里把这个目标叫 SLA-QPS：

为什么本机测不出这个数。因为施压机和被测机是同一台。JMeter 起 200 线程的时候它自己要吃 CPU，要吃连接，还得跟 MySQL 和 Redis 抢。这时候你去测"最大稳定 RPS"，测到的瓶颈很可能是施压脚本本身，或者是那台 Windows 的端口/线程上限。数字会低得可疑，也可能高得没道理，取决于你撞上哪个瓶颈。

结论很直接，做这个实验得有一台独立的施压机（或者云端被测 + 本机发压）。这一步我没做。方案里那行填空还是空的：

我要是写"能扛 200 QPS"，那是编的。目前【待你补充：需要独立施压环境】，规格写清楚才有资格填这个数。 同机能证明的，我只写它能证明的：机制生效（限流 55/60 拦下、MQ 不可达 50/50 成功）、扫描量下降（397293 → 50）、查询次数下降（6267 → 3）、尾延迟的相对变化（274ms → 6ms，同机同 jar 只差一个 bypass 开关）。这四类都不依赖"我的机器是不是瓶颈"这个问题。

7.3 还在的问题，按手记原样提

这部分我全部写成"当前实现"，一条都不写成设计亮点。 一、分布式锁的释放是裸 delete。

LOCK_EXPIRE_SECONDS = 10（:63）。问题在 releaseLock 那一句，它不比对锁是谁持有的，直接删。于是这条时序是成立的：A 拿锁，业务超过 10 秒，锁自动过期，B 拿到锁，A 业务做完了跑 finally 把 B 的锁删了，C 又能进来。互斥性在这一刻没了。 正确做法是 value 放一个持有者标识，释放时用 Lua 比对后再删，或者直接用 Redisson 的锁。这里没做。因为单机部署 + 缓存 key 粒度 + 10 秒 TTL 凑一起，这个窗口在我的场景里极窄，可那是运气不是设计。我按"当前实现"记这条，不美化。 同一段里还有个小东西：等锁失败的那条路径是 Thread.sleep(50)（:166）然后直接查 Redis，也就是说锁竞争的处理方式是"睡一下再看眼"。这在 LLM 那种几秒的耗时前完全不管用，不过缓存加载不是那种量级，我判断够用。 二、t_post_interaction.type 的三处描述互相矛盾（§3.3 已给表）：DDL 注释、实体 javadoc、实际代码三个说法，两处是错的。 三、t_circle_member 的角色语义有三处不一致：docs/sql/zhiyuan.sql:162 说 0/1/2 三个角色（含管理员，已废弃）、CircleMember.java:52 说"0-圈主，1-成员"（把两个值写反了）、CircleMemberConstants.java:9-10 说 ROLE_MEMBER=0/ROLE_OWNER=1（这个才是准的）。而且 V3_升级脚本.sql:160 那条"角色收敛"的 UPDATE 拿字符串比 tinyint，真跑会把圈主冲成成员。 四、贡献度只删了一半：VO 和 UI 删了，DB 列和实体字段留着，DROP COLUMN 那句被注释（§3.4）。 五、审核 fail-open（§4.5）：异常吞成"默认通过"；另一条 fail-closed 的实现是 orphan。 六、HTTP 发送端点跟"禁止 HTTP 兜底"的契约相反（§5.2）。 七、开了 MQ 之后圈子新帖通知必失败（§5.5），死信队列没人看，title 为 null。 八、白名单里留着三条已下线的路径，同时该免登录的两个地图端点不在名单里（§5.6）。 九、WebSocket 在线状态是单进程的（§2.3）：多实例部署时实时侧直接失效。 十、ShareLinkGenerator.domain 注入了但没用（§4.9）。 十一、业务 service 零测试（§6.1）。 十二、docs/架构设计文档.md 的架构图还画着已经不存在的网关节点（§5.3）。那张 mermaid 里 AuthFilter[AuthGlobalFilter]、RateLimit[RateLimitFilter]、TraceFilter[RequestTraceFilter] 三个节点在 :22-24，:983-987 还列了 5 个指向 gateway/src/... 的 file:/// 死链接，那五个文件今天 find 全部 0 命中。 这张清单我不想排序，排了就会变成"最紧急的三个"那种话术。有一个动作是明确的：第一、二、三条都是注释/文档跟代码相反，不是代码本身错。这类问题烦的地方在于，下一次的读者（可能就是三个月后的我）会相信注释，然后按错的语义去改代码。要收拾的话先从注释和 DDL 里的 COMMENT 收手，成本最低，误导也消得最多。别的我还没想好。
