核心代码的设计取舍

发表于2026-09-17|更新于2026-09-28|项目感悟

这篇旧版是我对着记忆写的，里面有一段"Lua 脚本原子释放锁"，配了完整脚本，写得很漂亮。这次逐行翻源码，releaseLock 实际长这样：

一行，裸删，没有 token，没有校验，锁过期慢了一步就会删掉别人刚加的锁。所以这一版所有取舍都按源码现在的样子讲，包括讲我自己把没做的事写成做过的事的那几处。代码全是仓库里的原文，路径都给你。

1. JwtAuthenticationFilter：白名单宁紧勿松

api/.../config/JwtAuthenticationFilter.java，全项目每个请求都要穿它。

取舍一：按精确路径放，不放整棵树。早期 /api/ai/**、/api/files/** 是整树放行的，后来收紧了——AI 是重资源调用，不鉴权等于把 token 配额挂在免费接口上让人刷；文件里只有 GET/HEAD 匿名（头像和帖子图总不能让游客登录看），上传删除必须登录。默认不放、有充分理由才放，这个方向我现在都不动摇。

取舍二：白名单路径带了 token 就顺带解析，解析失败不管。游客能看，登录后同一接口能多返回"是不是成员"这类字段，公开体验和登录增强之间最便宜的折中。

取舍三：finally { UserContext.clear(); } 写死。UserContext 是 ThreadLocal，Tomcat 线程池会复用线程，不清就是给下一个请求留上一个人的身份，这不是好习惯是铁律。

还有一条我旧版没敢说的：这个 Filter 不查黑名单。我以为它查，写"吊销"写了两个版本，源码里 blacklist 关键字在过滤器内 0 命中。

2. TokenManager：只写不读的黑名单，不是取舍是没做完

api/.../cache/manager/TokenManager.java，公开方法就两个：

storeToken 用 Hash 是真取舍：access 和 refresh 生命周期相同，分两把 key 就得记两次 TTL，漏一次就是永久 token，一把 key 一个过期时间，强一致。这个我认。

blacklist 我旧版写成了"有意的纵深防御设计，每请求查 Redis 成本大于收益"。逐行读完域01之后改口：它只写不读，refresh 也不轮换，登出后 access 在剩余有效期内照用，封禁用户的 status 字段在登录链路里查都没查——SQL 把"这个用户被封禁了"取到进程里，然后当场扔了。这不是取舍，是同一个人对"JWT 怎么吊销"这个问题三次尝试都没做完，留在那儿了。凡是"时间、长度、次数"这类数字，先问它有几份、哪份生效，我这验证码有效期就有四份口径。

3. PermissionAspect 加 PermissionContext：为什么注入 List 不注入 Map

api/.../permission/PermissionContext.java：

fail-closed 这条是真的，我对着源码核过，checker 漏注册就拒绝，权限系统的事故只可能出现在放行方向，这个方向我选死。

为什么用 @Autowired List 再 @PostConstruct 自建 EnumMap，不用 Spring 的 Map<String, X> 注入——因为被 Map 咬过。通知系统当初就写的 Map 注入，我以为 key 是业务类型码，其实 Spring 给的是 Bean 名，handlerMap.get("post_comment") 永远 null，所有通知静默蒸发，不报错。List 注入加自建路由表，key 完全自己说了算。

@RequirePermission 有 resourceIdParamName 和 relatedResourceIdParamName 两个参数也是被业务逼的：删评论得先确认你能不能看到那条评论所属的帖子，只知道评论 id 不够。注解支持 dto.circleId 点号取参，比 SpEL 直白。

但这个体系里躺着一个还活着的事故：FileController.deleteFile 的注解写的 resource = ResourceType.POST，校验 fileId——拿文件 id 去帖子表查归属，谁的帖子 id 撞上文件 id 谁就能删别人文件，真正的 FilePermissionChecker 注册在表里永远收不到请求。教训就一句，注册表这种东西，格子在不在不算数，得看有没有请求真的走得到那一格。

4. NotificationPublisherImpl：修好路由之后，还剩说谎的计数器

b183b68 之后的样子：注入 List<NotificationHandler>，启动时按每个 Handler 的 getSupportedTypes() 自建 typeToHandlerMap，查不到落 SystemHandler 兜底——用户收到一条怪消息，也比什么都没发生强。Handler 管"通知长什么样"，PushChannel 管"怎么送出去"，落库加 WS 两条通道正交，加短信只需要加 Channel。

type 用小写下划线字符串不用枚举，因为通知类型会随业务长，用枚举每加一种全链路跟着改。

没修的：send() 在循环里逐接收者 try/catch，通道推送失败，日志打了，successCount 照样加一，返回的"成功数"不可信。这个域现在对全部通知一视同仁地吞异常，按语义该分三档，还没分。

5. MultiLevelCache：缓存什么、什么时候动缓存、锁怎么放

api/.../cache/core/MultiLevelCache.java。压测开关：

这个开关是被"你怎么证明是缓存的作用"逼出来的，两套代码对比永远说不清，一份 jar 切配置才唯一变量。数字：100 RPS，P99 274ms 对 6ms，回源 6267 对 3。

只缓存帖子详情，不缓存列表，类注释里写了理由——列表查询维度组合太多，命中率低，不值得。这个克制我现在守得住，因为想清楚了一件事：不是所有 Redis 用法都叫缓存。

计数走 Redis INCR 加每 5 分钟对账回写 DB，不做 UPDATE like_count = like_count + 1——行锁串行化，还有刚删缓存就被并发写回旧值的问题。账本规矩：DB 冗余列是事实源，Redis 只是写缓冲，TTL 才是清理方。

事务提交后才动缓存（afterCommit），先写库、committed 后再删，删除比直接更新安全。这个顺序反过一次：先删缓存 DB 回滚，缓存里就留下"假数据"。

然后是我旧版吹过的那把锁。真实代码：SETNX 值写死 "1"，没抢到锁睡 50 毫秒，回查 L2，还没有就自己去查库；释放就是最上面那个裸 delete。"单飞防击穿"只在回源比 50 毫秒快的时候近似成立。防穿透的 NULL 占位也是真的，TTL 取原 TTL 的一成、下限 10 秒，防雪崩 jitter 是真的，防击穿这个件只能算装了半截。三个防我以后再没说"完整"。

6. 三个没写在代码里、但决定代码形状的取舍

删网关。gateway 模块活了 37 天，2026-05-22 建、2026-06-28 删，独立进程鉴权限流打链路号，需求里没有这条，是技术侧自己想上微服务标配。只有一个服务时，网关不是为未来做准备，是现在就多两个进程两份真相，白名单存两份还会漂移。删。

私信强制走 WS，禁止 HTTP 兜底发送。需求 7.6 写的。直觉上留个 HTTP 降级路更稳，但那条路一存在，故障就从可见变成不可见——前端悄悄成功，用户悄悄丢消息，这是最贵的一种退化。

离线消息什么都不做。直觉要建待投递队列，翻自己的表发现 t_private_message 本身就是那条不会丢的队列，再造一个队列就是凭空多一份要同步的副本，前端重连补拉一次 history 就完事。这不是偷懒，是需求允许的两个选项里更便宜的那个。

收尾不了的部分

这篇讲完我发现一件事，所谓取舍，一大半根本不是取舍。裸 delete 是不知道要校验，Map 注入是不知道 key 是 Bean 名，只写不读的黑名单是三次都没做完，这三处当时都不知道自己在选什么。真配得上"取舍"两个字的，就删网关、只缓详情、禁 HTTP 降级这几条，有得有失的那种。分不清哪条是哪种的时候，我现在就把代码逐行再读一遍，读到脸红为止。脸红哪处，哪处就是当年没想清楚的。就这样吧。
