前言

上一篇性能采集文章用的是 PowerShell 脚本 + Actuator 差值法，虽然拿到了服务器侧真实 QPS，但有两个硬伤：

  1. 没有对照组——只测了"有缓存"，没测"无缓存"，面试官一句"你怎么证明是缓存的作用？"就能把数据打回原形
  2. 并发量太低——50 并发 2 万次请求，根本看不到 MySQL 的真实承压

这次我直接用 JMeter 5.6.3，在真实 MySQL + Redis 环境下，对帖子详情接口做了 500 并发 × 90 秒 Duration 的四组控制变量压测，用数据证明多级缓存每一层的真实价值。

JMeter 使用 帕累托分布的 10 万帖子 ID（posts_pareto_100k.csv），模拟真实社区的长尾访问特征：少数热帖被高频访问，大量冷帖低频访问。不是 100 个固定 ID 那种"命中率虚高"的假压测。

三、压测方法：控制变量 + 稳态模式

3.1 统一参数

每组压测参数完全相同，仅改变缓存策略：

  • 并发：500 线程
  • Ramp-up：5 秒（短 ramp-up，快速达到目标并发）
  • 持续时间：90 秒（Duration 模式，非固定循环次数）
  • 预热丢弃：前 15 秒作为 JVM/连接池/缓存预热，只取 15~90 秒区间的稳态数据
  • 接口：GET /api/posts/{postId}（需 JWT 认证）
  • CSV：10 万帕累托分布帖子 ID，Sharing mode = All threads

4.2 关键对比

对比 QPS 变化 延迟变化 MySQL 查询变化
仅 Redis vs DB 基线 +213%（1,743 → 5,458） -68%（284 → 91 ms） -94%（155,105 → 9,478）

引入 Redis 后，MySQL 查询量从 15.5 万次 降至 9,478 次，降幅 **94%**。再叠加 Caffeine 本地缓存，QPS 进一步从 5,458 提升到 5,769。

注意 C/D 组 L2 命中极少——因为 L1 本地缓存已经拦截了 98% 的请求，只有 L1 未命中的长尾请求才会穿透到 Redis。

缓存平均查询耗时从 A 组的 2.67 ms 降到 C/D 组的 0.13~0.14 ms，下降了 **95%**。

五、数据质量：经得起拷问

5.1 Little's Law 校验

以稳态 QPS × 平均延迟估算并发数：

组别 QPS × 平均延迟 估算并发 JMeter 配置 结论
A 1,743 × 0.284 495 500 自洽
B 5,458 × 0.091 497 500 自洽
C 5,769 × 0.086 496 500 自洽
D 5,610 × 0.089 499 500 自洽

并发数与 JMeter 配置一致，数据物理上自洽。

5.2 多维度交叉验证

  1. **JMeter 请求数 ≈ 应用层 totalQueryCount**——误差 < 0.1%
  2. **应用层 dbQueryCount ≈ MySQL Queries_delta**——交叉吻合
  3. A 组请求量最少（284 ms 延迟导致线程在单位时间内发更少请求），B/C/D 组请求量更多——符合 Little's Law
  4. 所有服务真实在线：脚本启动前检查 3306/6379 端口，后端通过 actuator/health 确认 UP
  5. RabbitMQ 显式关闭排除变量干扰

5.3 关于 L1 本地缓存的延迟说明

面试官可能会问："C 组和 D 组为什么只差 2~3%，预热收益去哪了？L1 到底值不值？"

真实原因：

  1. 本机 Redis 走的是 localhost 回环网络，单次 RTT 约 0.1~0.3 ms，L1 的内存访问优势被极大稀释
  2. C 组冷启动后 L1 迅速被热点数据填满，因此与 D 组差异很小
  3. L1 的核心价值不只在单机延迟，更在保护 Redis 集群：C/D 组只有约 2% 的请求到达 Redis，Redis 查询压力从 B 组的 46.3 万次命中降至约 9 千次命中
  4. 在生产环境（远程 Redis、网络 2~5 ms、高并发）下，L1 的集群保护价值会进一步放大

六、可写入简历的数据

在 zhiyuan_Flow 项目中，针对帖子详情接口设计并执行了 10 万级真实数据、500 并发、90 秒 Duration 模式的四组控制变量压测：

  • 无缓存基线：QPS 1,743，平均延迟 284 ms，MySQL 承受 15.5 万次查询
  • 引入 Redis 后：QPS 5,458（+213%），平均延迟 91 ms（-68%），MySQL 查询降至 9,478 次（-94%），应用层缓存命中率 97.98%
  • 再叠加 Caffeine 本地缓存：L1 拦截 98% 以上请求，Redis 访问降至约 2%，QPS 提升至 5,769（+231% vs 基线），平均延迟 86 ms
  • 测试在真实 MySQL + Redis 环境下运行，0 错误，JMeter 请求数、应用缓存统计、MySQL delta 三类指标交叉验证一致
